## 5. Vulnerabilities

- No off-by-one/wraparound bugs found in the periodic indexing: `_corner_interval`'s `searchsortedlast`-based interval lookup and `_wrap_to_2pi` both handle the `j==0`/`j==m` wraparound cases explicitly and correctly (verified by inspection: `j==0` uses `corners[end]-2π`, `j==m` uses `corners[1]+2π`).
- Degenerate corner angle (`angle ≈ 0` or `2π`) is already guarded in two ways: (a) `_kress_smoothstep_prime`/`_kress_smoothstep_doubleprime` clamp `u` to `[eps(T), 1-eps(T)]` before doing `u^(q-1)`-type operations near the corner boundaries; (b) both grading functions retry with a reduced `q` (`while qT>one(T) ... minsep>=minsep_tol && return ...`) if the mapped nodes get too close, which is exactly the safety valve for near-degenerate configurations. **No blow-up found**, single-corner `_kress_w`/`_kress_wprime` were hand-checked at `s=0`/`s=2π` (denominator `a+b` never vanishes there since one of the two terms evaluates to `1`).
- **Minor edge case (new, low severity)**: `_sort_unique_corners` merges any two corners within `sqrt(eps(T))` (~1.5e-8 for `Float64`) of each other, treating them as duplicates. If a billiard genuinely has two distinct true corners that close together (not a numerical duplicate), one would be silently dropped rather than erroring. Unlikely for realistic geometries but not explicitly guarded/documented as a limitation.

## 6. Consolidation opportunities

- The **q-retry-with-warning control-flow block** (`while qT>one(T) ... minsep=_min_periodic_spacing_sorted(...) ... minsep>=minsep_tol && return ... qnew = max(one(T),qT*0.9); @warn ...; qT = qnew end; error(...)`) is duplicated near-verbatim between `kress_graded_nodes_data` and `multi_kress_graded_nodes_data`. This is a legitimate, behavior-preserving consolidation opportunity — extract into a shared helper that takes a per-`q` node-generation closure, since the *retry policy* is identical even though the underlying grading math differs.
- The **grading formulas themselves should NOT be merged**: single-corner `_kress_v`/`_kress_w` (cubic-polynomial Kress construction) and multi-corner `_kress_smoothstep` (power-law `u^q/(u^q+(1-u)^q)`) are mathematically different constructions that happen to serve the same clustering purpose. `kress_graded_nodes_data` cannot simply delegate to `multi_kress_graded_nodes_data(T,N,[0.0];...)` without changing numerical output — flagging this only as "don't consolidate the math," not as an issue.
- `_min_periodic_spacing_sorted` is already correctly shared between both functions — no duplication there.

## 8. Performance note (flag only, not a fix)

- **[kressgrading.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/quadrature/kressgrading.jl#L27-L29) / [kressgrading.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/quadrature/kressgrading.jl#L52-L54)** — **new finding, most significant one.** Inside `kress_R_even!`/`kress_R_odd!`, the column-fill loop `@views R0[:,j] .= circshift(R0[:,j-1], 1)` calls `circshift`, which **allocates a fresh length-`N` array on every iteration**, for `N-1` iterations per call. Since `kress_R!` is called on every `construct_matrices` invocation of every BIM solver (`dlp.jl`, `cfie.jl`, `ebim.jl`, `beyn.jl`, `compositebim.jl` — confirmed via grep) and `N` is the full boundary discretization size, this is `O(N)` allocations of `O(N)` elements each = `O(N²)` avoidable memory traffic on a hot path that should otherwise be `O(N²)` total work but `O(1)` extra allocations. `circshift!(dest, src, 1)` (in-place, using a single scratch buffer reused across the loop) would eliminate this entirely.
- `a = zeros(Complex{T}, N)` and the `FFTW.ifft(a)` result (`rjn`) are also allocated fresh per call in both `kress_R_even!`/`kress_R_odd!` — lower priority than the `circshift` issue since it's `O(1)` such allocations per call, not `O(N)`.
- `kress_graded_nodes_data`/`multi_kress_graded_nodes_data` allocate 5 fresh output vectors per call inside the `while` loop, so a degenerate-geometry retry reallocates all 5 again — acceptable since these are one-time discretization-setup calls (not per-iteration), and the returned arrays must be freshly allocated regardless.
- `FourierNodes.sample_points`'s `push!`-based accumulation into `Vector{Vector{T}}` is not on a per-iteration hot path (called once per basis/solver setup) — lower priority.
