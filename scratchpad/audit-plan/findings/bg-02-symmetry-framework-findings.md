## 2. Missing wiring

- **`apply_symmetry_pb` has no `AbsRotation`/`NFoldRotation` method** — [symmetry.jl:137](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetry.jl#L137) declares `apply_symmetry_pb(sym::AbsReflection, ...)` only. `pb_sectors`/`pb_coords` ([poincarebirkhoff.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/poincarebirkhoff.jl#L25-L47)) call `symmetry_of(billiard.symmetries, sym_sector-1)` then `apply_symmetry_pb(sym, ...)` for **every** registered generator, including `NFoldRotation` instances on `C3Billiard`/`StarBilliard` (registered via `Cn_symmetry`). Since `NFoldRotation <: AbsRotation`, **not** `<: AbsReflection`, this is a guaranteed `MethodError` at runtime. **New finding, not previously tracked** (geometry-audit-10.9.md and the Step-15/16 plans discuss `apply_symmetry`/`symmetry_index_orbits` extensibility but never audited `apply_symmetry_pb` against rotation billiards). This is a genuine "symmetry that doesn't work" per the user's stated concern: bg-01's findings confirm `pb_sectors(billiard)` is unconditionally called by [QBPlotting.jl/husimiplotting.jl](/home/clozej/.julia/dev/QBPlotting.jl/src/husimiplotting.jl#L9) and `boundaryfunctionsplotting.jl` for **any** billiard passed to `plot_husimi_function!` — so Husimi-function plotting crashes today for `C3Billiard`/`StarBilliard` specifically because of this file's dispatch gap.
- Compounding this: `apply_symmetry_pb`'s body never actually reads its `sym` argument — it dispatches only on `sym_sector ∈ {1,2,3,4}` with hardcoded `2L-s`/`2L+s`/`4L-s` reflection formulas. This only happens to be correct because every `D2_symmetry()`-based billiard registers exactly 3 elements in the fixed order `[Y,XY,X]` (so `sym_sector 2,3,4` always land on the right formula by coincidence of ordering, not by reading `sym`). It is not generalizable to `Cn_symmetry(n)` for any `n` (wrong transformation shape, and only sectors 1–4 are handled regardless of `n`). This is a design gap that predates but was never closed by the Step 15 rotation-wall support (`SymmetryWall` was extended to cover rotation walls, but `apply_symmetry_pb` was not).
- Every reflection/rotation type otherwise has the full documented dispatch trio (`apply_symmetry`, `symmetry_node_multiple`+`symmetry_index_orbits`, `_apply_symmetry_to_curve`/`_orientation_reversing`+`_sym_matrix`) — verified present for `XAxisReflection`/`YAxisReflection`/`XYAxisReflection`/`DiagonalReflection`/`AntiDiagonalReflection`/`NFoldRotation`. **No regression** from the geometry-audit-10.9.md verdict.

Gap 2 remains open exactly as documented.
  - Checked the specific concern raised: `CompositeBIMSolver.construct_matrices` ([compositebim.jl:449](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/compositebim.jl#L449)) does call `_fold_boundary(T, pts.xy, solver.symmetry, solver.character)` → `symmetry_index_orbits(T, pts.xy, solver.symmetry, ...)` on `pts.xy`, which for a multi-ring billiard would be the **flattened concatenation of all rings' points**, treated as one contiguous ring by the exact-integer-permutation formulas (`_idx_reflect_x(q,N) = mod1(N-q+1,N)` etc., [symmetryorbits.jl:113-118](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetryorbits.jl#L113-L118)). **This is silently wrong, not a loud error**: there is no check anywhere that a multi-component `pts` is single-ring before this call, so if a future symmetric multiply-connected billiard is combined with `CompositeBIMSolver(...; symmetry=...)`, it would silently compute a nonsense index fold rather than throwing. Currently unexercised only because no billiard triggers this combination.

## 4. Unstable APIs

- **New finding — all reflection transforms are hardcoded to `Float64`, not generic over the caller's `T`**: `reflect_x`/`reflect_y`/`reflect_diag`/`reflect_antidiag`/`reflect_xy` ([symmetry.jl:3-7](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetry.jl#L3-L7)) are module-level `LinearMap{SMatrix{2,2,Float64,4}}` constants. Every `apply_symmetry(sym::<Reflection>, pt::SVector{2,T})` (e.g. [symmetry.jl:108-131](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetry.jl#L108-L131)) applies one of these to an arbitrary-`T` point, producing a `Float64`-promoted result regardless of `T`. `_apply_symmetry_to_curve` for `LineSegment` ([fullboundary.jl:52-56](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/fullboundary.jl#L52-L56)) re-wraps the result in `SVector{2,T}(...)`, which silently **narrows precision to `Float64` and back** for a `BigFloat`-typed billiard (real correctness/precision issue, not just a stylistic type-instability one) and creates an unnecessary type-widen/narrow round-trip for `Float32`. This violates the project's "concrete type parameters propagated from inputs" convention and was not flagged by the prior 10.9 audit.
- **`NFoldRotation`** ([symmetry.jl:179-186](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetry.jl#L179-L186)) has the same issue at the struct level: `angle::Float64` and `sym_map::LinearMap{SMatrix{2,2,Float64,4}}` are hardcoded, even though `C3Billiard{T}`/`StarBilliard{T}` are generic over `T<:Real`. Same precision-narrowing/widening consequence as above for non-`Float64` rotation billiards.
- `SymmetryRegistry`/`SymmetryWall`/`XAxisReflection`/etc. `sym_id`/`sector_id` fields are all concrete `Int`/`Int64` (aliased on 64-bit systems) — **no `Union{Nothing,Int}` inconsistency found**, confirmed clean.
- `symmetry_of` ([symmetryregistry.jl:73-77](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetryregistry.jl#L73-L77)) throws a clear `ArgumentError` on an unmatched `sym_id` — stable, not a silent-`nothing` footgun.

## 6. Consolidation opportunities

- **New finding**: `apply_symmetry` for `XAxisReflection`/`YAxisReflection`/`XYAxisReflection`/`DiagonalReflection`/`AntiDiagonalReflection` ([symmetry.jl:108-131](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetry.jl#L108-L131)) is 10 near-identical methods (2 per type: single-point and vector-of-points) that only differ in which module-level `LinearMap` constant is applied. `fullboundary.jl` already has exactly the per-type trait table this calls for (`_sym_matrix(sym)`, [fullboundary.jl:36-41](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/fullboundary.jl#L36-L41)). A single generic `apply_symmetry(sym::AbsReflection, pt::SVector{2,T}) where T = SVector{2,T}(_sym_matrix(sym)*pt)` (plus one broadcasting method) would replace all 10, provided `_sym_matrix`/the module-level reflection constants are moved earlier (before `apply_symmetry`'s definition site) — also solves the `Float64`-hardcoding weakness in §4 for free if `_sym_matrix` is made to promote to `T`.
- **New finding**: `symmetry_index_orbits` for `XAxisReflection`/`YAxisReflection`/`DiagonalReflection`/`AntiDiagonalReflection` ([symmetryorbits.jl:181-192](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetryorbits.jl#L181-L192), [symmetryorbits.jl:229-247](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetryorbits.jl#L229-L247)) are 4 near-identical two-element-orbit constructions differing only in the index-permutation function (`_idx_reflect_x`/`_idx_reflect_y`/`_idx_reflect_diag_plus`/`_idx_reflect_diag_minus`) and the divisibility-check error message. Could be one generic method parametrized by a `perm_fn` looked up via a small per-type trait (mirrors `_sym_matrix`'s existing pattern) — not urgent, but a real 4x duplication.
- `_apply_symmetry_to_curve`/`_reverse_curve` for `FourierCoeffPolarSegment` vs. `PolarSegment` ([fullboundary.jl:107-135](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/fullboundary.jl#L107-L135)) are already well-consolidated via the shared `_polar_symmetry_image` helper — no further action needed there.
