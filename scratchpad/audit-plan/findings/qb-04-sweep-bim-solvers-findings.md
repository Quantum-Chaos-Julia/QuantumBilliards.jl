## Unstable APIs
- **`ParticularSolutionsMethod.sampler::Vector`** ([particularsolutions.jl#L44](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/particularsolutions.jl#L44)) is declared as the bare abstract `Vector` (no element-type parameter), not `Vector{<:AbsSampler}`. Every read of `solver.sampler[i]` is therefore dynamically dispatched/boxed — a genuine abstractly-typed-field violation of this mode's type-stability convention. It mirrors `DecompositionMethodSolver`'s identical `sampler::Vector` field (out of this step's scope, used as PSM's structural template per the `julia-add-solver` skill's "mirror the closest sibling" rule) — so it's a pre-existing pattern being faithfully replicated, not a new regression, but worth fixing in both places together if ever revisited.
- **Struct field order for PSM vs. its `SweepBasisSolver` sibling**: `DecompositionMethodSolver` orders trailing fields `eps, min_dim, min_pts, rellich_origin`; PSM instead inserts its extra field (`int_pts_scaling_factor`) *before* `sampler`/`eps`/`min_dim`/`min_pts` rather than after all six load-bearing fields as the `julia-add-solver` skill recommends ("add extra fields as trailing"). This causes no functional bug (field access is name-based, not positional, and PSM's own constructors are internally consistent), but it's a minor consistency deviation from the skill's stated convention.
- **`DoubleLayerPotentialSolver`/`CombinedFieldIntegralEquationSolver` constructor signatures and field order are excellently consistent with each other**: identical field list/order (`pts_scaling_factor, min_pts, grading, symmetry, character, eps`), identical keyword defaults, identical `(pts_scaling_factor, billiard, sector::SymmetrySector)` validated-constructor overload. `CompositeBIMSolver`'s different shape (`component_solvers, symmetry, character`, no `pts_scaling_factor`/`grading`/`eps` of its own) is appropriately different since it's a *wrapper* over other `SweepBIMSolver`s, not a standalone kernel — matches the skill's "struct shape is determined by the class of methods" principle correctly.
- **`symmetry::Sy where Sy<:Union{AbsSymmetry,Nothing}` is *not* a runtime type-instability** despite the `Union` appearance — since `Sy` is a struct type parameter, every concrete solver instance has a concretely-known `Sy` (e.g. `Nothing` or a specific `AbsSymmetry` subtype), so `solver.symmetry === nothing` branches are resolved at compile time per specialization, not at runtime. Worth stating explicitly since the audit checklist specifically asked to look for this failure mode — it does not apply here.

## Vulnerabilities
- **KrylovKit convergence info is discarded everywhere it's called.** Every one of `solve`/`solve_vect` in [dlp.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/dlp.jl#L354-L372), [cfie.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/cfie.jl#L419-L436), [compositebim.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/compositebim.jl#L480-L497), plus `solve_state` in [sweepmethods.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/sweepmethods.jl#L294), calls `KrylovKit.svdsolve(A, 1, :SR)` and discards the fourth return value (`_`), which is exactly the `info` object reporting whether the requested singular value/vector actually converged. A genuinely non-convergent Lanczos iteration (plausible near an ill-conditioned/near-degenerate `A(k)`, e.g. very close to a true eigenvalue, or for a poorly separated smallest singular value) is silently accepted as if `vals[1]` were accurate — no code path anywhere checks `info.converged`. This matches the checklist's "silent non-convergence swallowed" concern precisely and applies uniformly across all three BIM kernels.
- **No degeneracy/conditioning safeguard for requesting only 1 singular value.** `svdsolve(A, 1, :SR)` always asks for exactly the single smallest singular triplet. At a genuinely (near-)degenerate wavenumber — physically common for symmetric billiards when `symmetry` is *not* used to split the spectrum, or for accidental degeneracies — the true smallest singular value can have multiplicity ≥ 2, in which case the single returned right singular vector is an arbitrary, uncontrolled mix of the degenerate eigenspace rather than a well-defined eigenstate; nothing checks whether a second-smallest singular value is nearly equal to the first to warn the caller. This is inherent to the `nsv=1` Krylov call convention used identically by all three solvers, not a one-off bug.
- Everything else already identified generically by `qb-01`/`qb-03` (the `@blas_1`/`@blas_multi_then_1` non-restoring, non-exception-safe BLAS thread count race) applies again here: `dlp.jl`, `cfie.jl`, `compositebim.jl`'s `solve`/`solve_vect`, and `particularsolutions.jl`'s `construct_matrices`/`solve_full`/`solve_with_rank_reduction`/`solve_vect` are all additional call sites of that same pre-existing macro weakness — flagged for completeness of this step's file set, not re-analyzed.

## Consolidation opportunities
- **`_cfie_evaluate_points(solver, ::SmoothPeriodicGrading, ...)` and `_cfie_evaluate_points_graded(solver, ::GlobalCornerGrading, ...)` in [cfie.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/cfie.jl#L107-L163) are byte-for-byte identical to `_dlp_evaluate_points`/`_dlp_evaluate_points_graded` in [dlp.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/dlp.jl#L120-L177)**, differing only in which solver type triggers dispatch — both only ever read `solver.pts_scaling_factor[1]`, `solver.min_pts`, `solver.symmetry`. This is a genuine copy-paste duplication, not "DLP + one extra term" — [06-cfie-solver.md](../../../Programs/QuantumBilliardsTests/scratchpad/migration-plan/06-cfie-solver.md) never actually anticipated the *point-sampling* code needing to be shared (only the kernel), but since these bodies are identical they should be lifted into one shared helper (e.g. parametrized on `solver::SweepBIMSolver` or accepting the three fields directly) rather than living twice.
- **The D(k) kernel algebra itself is duplicated, not shared, contrary to the migration plan's explicit design intent.** [06-cfie-solver.md](../../../Programs/QuantumBilliardsTests/scratchpad/migration-plan/06-cfie-solver.md#L36-L45) explicitly proposed factoring `D(k)` into a shared internal helper reused by both `DoubleLayerPotentialSolver` and `CombinedFieldIntegralEquationSolver`'s `construct_matrices`. In practice, `_cfie_fredholm_full!`/`_cfie_kernel_entry` in [cfie.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/cfie.jl#L228-L293) re-derive the exact same `αL1, αL2, l1, l2` double-layer formula found in `_dlp_fredholm_full!`/`_dlp_kernel_entry` in [dlp.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/dlp.jl#L212-L262) verbatim, instead of calling into it. (The *reduced-branch* code does at least reuse `_dlp_kernel_entry`/`_cfie_kernel_entry` via dispatch from `compositebim.jl` — it's specifically the two dense "full" assembly functions and the CFIE kernel-entry helper that re-derive rather than call the DLP version.) A shared `@inline` scalar helper computing `(l1, l2)` from `(αL1, αL2, inn, j1, h1, invr, lt)`, called by both `_dlp_fredholm_full!`/`_dlp_kernel_entry` and `_cfie_fredholm_full!`/`_cfie_kernel_entry`, would remove the duplication without any allocation or performance cost.
- **`boundary_matrix_size(solver, pts)` is defined identically three times** — in [dlp.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/dlp.jl#L288-L296), [cfie.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/cfie.jl#L338-L346), and [compositebim.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/compositebim.jl#L365-L372), all with the exact same body (`solver.symmetry === nothing ? boundary_matrix_size(pts) : fundamental_size(symmetry_index_orbits(...))`). Since all three solvers uniformly expose `symmetry`/`character`, this could be one generic method on `AbsBIMSolver` (or a shared trait) in [sweepmethods.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/sweepmethods.jl) instead of three copies.

## Threading/BLAS
- `dlp.jl`/`cfie.jl`'s dense/reduced Fredholm assembly loops (`_dlp_fredholm_full!`/`_cfie_fredholm_full!`/`*_reduced!`) and `compositebim.jl`'s diagonal-block, cross-block, and reduced assembly loops all use a single `@use_threads multithreading=(multithreaded && N>=...)` outer level with a plain `@inbounds` (unthreaded) inner loop — no nested `Threads.@threads`, consistent with the mode's single-parallel-level convention.
- No BLAS calls occur inside any `@use_threads` region in these five files (the custom scalar Hankel/Bessel kernel loops don't call BLAS) — the only BLAS/Krylov calls (`svdvals`, `KrylovKit.svdsolve`, `qr!`/`LAPACK.gesvd!` in PSM) happen strictly after `construct_matrices` returns, each correctly wrapped in `@blas_multi_then_1`/`@blas_1`/`@blas_multi` per the existing convention (inheriting, not introducing, the qb-01-flagged BLAS-thread-race weakness).
- `compositebim.jl`'s outer loop over `nc` components (diagonal-block and cross-block component pairs) is intentionally left unthreaded — correct, since `nc` (number of connected boundary components) is always small, and threading the inner per-point loop is the right granularity.
