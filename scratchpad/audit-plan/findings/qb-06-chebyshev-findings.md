Their sole helper `_dlp_kernel_entry_cheb`/`_cfie_kernel_entry_cheb` is called only from within the also-dead `_*_reduced_cheb!`, so the entire subtree is unreachable from any live solver. This looks like fallout from Finding 2's rewrite: `BeynSolver` now exclusively uses the multi-k batch path (even for `Mk=1`), `ExpandedBIMSolver` never needed a value-only path (always derivatives), and plain `DoubleLayerPotentialSolver`/`CombinedFieldIntegralEquationSolver` don't have a `use_chebyshev` field at all — so nothing left to call these. Likely ported speculatively alongside the vector variant; candidate for removal.

## 8. Performance note (not a fix)

Item (2)'s Beyn multi-pass gap is **fixed**, so it is **no longer the dominant avoidable cost** in the Chebyshev-accelerated path — the multi-k assembly now streams the O(N²) pairwise-geometry cache exactly once per `construct_matrices` call regardless of `nq` (default 48), with per-thread `h1_tls`/`j1_tls` (or `h0/h1/j0/j1_tls` for CFIE) buffers reused across the whole pass. Remaining costs, roughly in order of likely significance for a large boundary discretization:
1. The O(N²) inner double loop itself (unavoidable — same cost as the non-Chebyshev direct-evaluation path, just with `_cheb_clenshaw` calls instead of `SpecialFunctions.besselh`/`besselj`).
2. `tune_dlp_cheb_plans`/`tune_cfie_cheb_plans`'s auto-tuning loop (`optimalpanelization.jl`), which itself does up to `cfg.max_iter` rebuild-and-validate iterations, each rebuilding `nz` full plans (`Threads.@threads` over wavenumbers) and re-checking `cfg.sampling_points` radii per plan — this is a one-time-per-window cost, not per-pair, but for `BeynSolver`'s per-window auto-tune (matching migration plan 10's implementation step 6) it repeats once per Weyl window in `compute_spectrum`. Item (3)'s panel-index cache would not address this cost (it's about panel-index lookup reuse across the O(N²) loop, not the tuning loop).
3. Item (3) (still open) and item (5) (still open) are both, as the 10.5 plan itself states, minor/negligible compared to (1)-(2) — O(1) arithmetic per pair — and remain reasonable to defer; nothing in this step's reading contradicts that prioritization.
