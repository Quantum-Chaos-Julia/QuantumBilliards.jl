# 2026-09-14 — Step qb-02: Basis functions (plane waves & corner-adapted Fourier–Bessel)

## Use case: Package-wide audit (explicit user request) — Step qb-02: Basis functions

Scope: [realplanewaves.jl](../../../.julia/dev/QuantumBilliards.jl/src/basis/planewaves/realplanewaves.jl), [corneradapted.jl](../../../.julia/dev/QuantumBilliards.jl/src/basis/fourierbessel/corneradapted.jl), cross-checked against [abstracttypes.jl](../../../.julia/dev/QuantumBilliards.jl/src/abstracttypes.jl)'s `AbsBasis` contract. Read-only — no files were edited. All findings below were empirically verified by running code against the live package (not just read), given the severity of what turned up.

## Dead code
- [corneradapted.jl](../../../.julia/dev/QuantumBilliards.jl/src/basis/fourierbessel/corneradapted.jl#L134): `CornerAdaptedFourierBessel.symmetries` is stored and threaded through `resize_basis` ([L251](../../../.julia/dev/QuantumBilliards.jl/src/basis/fourierbessel/corneradapted.jl#L251)), but is **never read by any evaluation method** — `basis_fun`, `gradient`, `basis_and_gradient`, `dk_fun` (both single-index and batch overloads) never touch `basis.symmetries`. Unlike `RealPlaneWaves` (where `symmetries`/`sym_qnumbers` genuinely drive `parity_pattern`), this field is pure decoration on `CornerAdaptedFourierBessel` — setting it to any value has zero effect on the actual basis functions produced.
- The `Sy` type parameter (`CornerAdaptedFourierBessel{T,Sy} ... where {Sy<:Union{AbsSymmetry,Nothing}}`) is **never dispatched on anywhere** in the codebase (verified by search — every method signature uses `CornerAdaptedFourierBessel{T}`, never `{T,Sy}`), and every one of the four constructors hardcodes it to `CornerAdaptedFourierBessel{Float64,Nothing}` regardless of what's actually passed as `symmetry`. Confirmed empirically: passing `symmetry = Any["fake_symmetry_marker"]` produces a struct whose type parameter still reads `Nothing` while `basis.symmetries` holds the real vector — the type parameter is not just dead, it is actively wrong/misleading. See Unstable APIs below for why this also isn't just cosmetic.

## Missing wiring
- Both concrete types implement all four documented `AbsBasis` methods (`resize_basis`, `basis_fun`, `gradient`, `basis_and_gradient`) and both are exported ([QuantumBilliards.jl#L29,31-32](../../../.julia/dev/QuantumBilliards.jl/src/QuantumBilliards.jl#L29)). No gap here.

## Missing implementations
- **Confirmed, reproduced live**: an `NFoldRotation` `SymmetrySector` is **silently ignored, not rejected**, by `RealPlaneWaves(dim, billiard, sector)`. Running
  ```julia
  b = C3Billiard(1.0)
  sector = symmetry_sector(b, BilliardGeometry.NFoldRotation=>1)
  basis = RealPlaneWaves(20, b, sector)
  ```
  gives `basis.symmetries === nothing`, `basis.dim == 80` (the full, unrestricted 4-quadrant basis) — no error, no warning, despite the caller explicitly requesting a `Z3` rotation-sector representation. This is exactly the "silent wrong result" failure mode migration-plan [16-bim-symmetrysector-migration.md](../../../migration-plan/16-bim-symmetrysector-migration.md)'s "Explicit, deliberate non-goal" section flags as a real gap for a future follow-up — confirmed still true, and confirmed to be the *worse* of the two possible outcomes (silent, not a clear error). [realplanewaves.jl#L234-L237](../../../.julia/dev/QuantumBilliards.jl/src/basis/planewaves/realplanewaves.jl#L234-L237) only ever looks for `XAxisReflection`/`YAxisReflection` matches; a rotation-only sector simply matches nothing and falls through to the "no symmetry" branch.
- `CornerAdaptedFourierBessel` has **zero** `(dim, billiard, sector::SymmetrySector)` constructor at all (confirmed by search — only `RealPlaneWaves` has one). Its own legacy `symmetries::Union{Vector{Any},Nothing}` field is untyped, disconnected from `SymmetrySector` entirely, and (per Dead code above) not even consulted by evaluation. So for corner-adapted bases the gap is total, not partial: no reflection sectors, no rotation sectors, nothing — worse than `RealPlaneWaves`'s partial (reflection-only) support. No stub/partial attempt exists.

## Unstable APIs
- **Confirmed, severe**: `CornerAdaptedFourierBessel`'s type parameter `T` is **not actually propagated from input** — every one of its four constructors hardcodes `CornerAdaptedFourierBessel{Float64,Nothing}(...)` regardless of the element type of `corner_angle`/`origin`/`rot_angle`. Reproduced live:
  ```julia
  CornerAdaptedFourierBessel(10, Float32(pi/4), SVector{2,Float32}(0,0), Float32(0))
  # ERROR: MethodError: Cannot `convert` an object of type PolarCS{Float32} to PolarCS{Float64}
  ```
  This means **`toFloat32` itself is broken** ([corneradapted.jl#L230](../../../.julia/dev/QuantumBilliards.jl/src/basis/fourierbessel/corneradapted.jl#L230) calls the constructor with `Float32` args, hitting the exact same crash) — the one function whose entire purpose is producing a `Float32` basis cannot succeed. Any caller trying to build a non-`Float64` corner-adapted basis (`Float32` for speed, `BigFloat` for precision) gets an opaque `convert` `MethodError` deep in the generated inner constructor, not a clear error at the call site. This directly contradicts `RealPlaneWaves`'s constructor, which correctly derives its type parameters from the input (`RealPlaneWaves{eltype(angles), Sa}`). This is the most significant weakness found in this step and should be prioritized over the smaller style items below.
- `dim`'s **meaning differs between the two types** with no doc cross-reference: for `RealPlaneWaves`, `dim` is "number of sampled angles" and the *actual* basis size is `dim * pl` (`pl ∈ {1,2,4}` depending on symmetry) — confirmed above (`RealPlaneWaves(20, ...)` on a no-symmetry request yields `dim=80`). For `CornerAdaptedFourierBessel`, `dim` is literally the basis size, unchanged. A solver or user treating `AbsBasis.dim` uniformly across basis types will silently get differently-scaled results. Not fixable without an API break; at minimum worth a doc note on `AbsBasis`'s interface contract in [abstracttypes.jl](../../../.julia/dev/QuantumBilliards.jl/src/abstracttypes.jl) that `dim` is basis-type-defined and not directly comparable.
- Minor, cosmetic constructor inconsistency: `RealPlaneWaves(dim::Int, ...)` vs. `CornerAdaptedFourierBessel(dim::Int64, ...)` — `Int`/`Int64` are identical aliases on this platform, not a real bug, just a spelling inconsistency worth normalizing if either file is touched again.
- `@inline` usage is inconsistent within and across both files: single-index `basis_fun` is `@inline` in both types, but `gradient`/`basis_and_gradient` (single-index and batch) are plain `function` in `RealPlaneWaves`, while `CornerAdaptedFourierBessel`'s batch `basis_fun`/`dk_fun` are `@inline` but its `gradient`/`basis_and_gradient` (single and batch) are not. Low severity, but worth flagging as unprincipled rather than a considered choice.
- Hot-path allocation: batch `basis_fun`/`gradient`/`basis_and_gradient` in both types correctly preallocate one output `Matrix{T}` and write via `@view` columns inside `@use_threads` — no per-column allocation, matches the mode's memory-efficiency convention. ✓ No violation here.

## Vulnerabilities
- **Confirmed, silent data corruption path**: `CornerAdaptedFourierBessel`'s `corner_angle` is completely unvalidated. `corner_angle = 0.0` silently produces `nu = Inf` (no error at construction); `corner_angle` negative silently produces a negative `nu` and is accepted without complaint. Both values then flow uncaught into `Jv(nu, k*r)`/`ca_fb`/`gradient`, producing either `NaN`/`Inf`-poisoned output or a basis that silently fails to satisfy the Dirichlet condition the whole construction is built around — with no error anywhere in the call chain. This is a real correctness risk for any caller that computes `corner_angle` programmatically (e.g. from a degenerate/misconfigured billiard geometry) and would benefit from an assertion (`0 < corner_angle`, and arguably `≤ 2π`) at construction time.
- `RealPlaneWaves(dim)` with a negative `dim` does error, but only incidentally, via an unrelated `ArgumentError("range(...): negative length")` raised deep inside `sample_points` — not a clear, targeted message about `dim` needing to be positive. Low severity (it does fail loudly, just unhelpfully) but worth a direct `dim > 0` check at the top of the constructor for a clearer error.
- The `NFoldRotation`-sector silent-ignore behavior documented under Missing implementations above is also a vulnerability in its own right: a caller who requests a rotation sector and gets back a full, unrestricted basis with no indication anything went wrong could unknowingly run an entire solve on the wrong representation.

## Consolidation opportunities
- The `(outer @use_threads over indices) → (inner @inbounds @simd/@inbounds loop over points, write via @view column)` skeleton is repeated near-verbatim ~7 times across the two files (`RealPlaneWaves`: `basis_fun`, `gradient`, `basis_and_gradient`; `CornerAdaptedFourierBessel`: `basis_fun`, `dk_fun`, `gradient`, `basis_and_gradient`). This is real duplication, but per the mode's "numerical physics first" / macro-opportunity guidance, abstracting it into a shared higher-order helper would trade explicit, auditable math for indirection in exactly the kind of hot, correctness-critical loop the conventions say to keep explicit — flagging only as a low-priority "known duplication, not recommended to touch" rather than a concrete suggestion.
- No duplicated logic worth extracting was found between the two files' actual mathematical content (cos/sin pattern selection is `RealPlaneWaves`-specific; Bessel-function/polar-coordinate logic is `CornerAdaptedFourierBessel`-specific) — the shared coordinate-transform helper (`_polar_coords!`) is already correctly factored into `utils/coordinatesystems.jl` and reused, not duplicated.

## Threading
- Both types' batch matrix-filling paths (`basis_fun`, `gradient`, `basis_and_gradient`, and `CornerAdaptedFourierBessel`'s `dk_fun`) use exactly one `@use_threads multithreading=multithreaded for c in 1:N ... end` outer loop over independent columns/indices, with a single-threaded `@inbounds @simd`/`@inbounds` inner loop over points and disjoint per-column `@view` writes — no nested threading, no overlapping writes. Fully compliant with the mode's threading convention in both files.

Everything else (dead `symmetries` field/type param, `dim` semantic mismatch, corner-angle validation, export/internal-candidate items) is lower severity or purely informational for a later step.
