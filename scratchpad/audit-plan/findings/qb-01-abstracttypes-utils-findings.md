## Unstable APIs
- No abstract type in `abstracttypes.jl` declares fields — all are pure interface markers. ✓.
- `utils/typeutils.jl` [`set_precision`](../../../.julia/dev/QuantumBilliards.jl/src/utils/typeutils.jl#L2-L5): dispatches only via a runtime `t == Float32` check, defaulting every other type (including `Complex{Float32}`, `Complex{Float64}`, `BigFloat`) to a hardcoded `convert(t, 1e-16)`. Consequences:
  - `Complex{Float32}` gets the `1e-16`-scale threshold instead of the `1e-8` used for plain `Float32` — inconsistent precision floor for complex vs. real single-precision data (Float32 noise floor is ~1e-7, so a `1e-16` threshold would essentially never filter anything for a `Complex{Float32}` state).
  - `BigFloat` gets a hardcoded `1e-16` regardless of its actual (much smaller) working precision — not incorrect, just needlessly conservative/non-scaling.
  - No `Any`-typed arguments/returns (the untyped `a` is fine — idiomatic Julia specialization per call site), so this isn't a type-stability violation, but it is a correctness/consistency weakness in a function that sits directly under the "correctness bar" this step is meant to enforce.
- `utils/billiardutils.jl` [L34](../../../.julia/dev/QuantumBilliards.jl/src/utils/billiardutils.jl#L34): `bcs = Vector{AbsBoundaryCondition}(undef,3)` builds a vector of an **abstract** element type — every element access requires dynamic dispatch/boxing. Low severity (3-element vector, built once per triangle construction, not a hot loop), but it's the one abstractly-typed container in the reviewed scope and worth a one-line fix (`Vector{Union{QuantumSolverIgnore,SpecularReflection}}` or similar concrete union) if this code is ever touched again.
- No `Any`-typed arguments/returns found in `geometryutils.jl`, `coordinatesystems.jl`, or `macros.jl`.

## Vulnerabilities
- `utils/macros.jl` — `@blas_1` ([L58-L63](../../../.julia/dev/QuantumBilliards.jl/src/utils/macros.jl#L58-L63)) and `@blas_multi_then_1` ([L67-L73](../../../.julia/dev/QuantumBilliards.jl/src/utils/macros.jl#L67-L73)) are **not exception-safe**: they set `BLAS.set_num_threads(...)` before running `expr` with no `try/finally`. If `expr` throws, the global BLAS thread count is left in the wrong state for the rest of the process. `@blas_multi` ([L48-L56](../../../.julia/dev/QuantumBilliards.jl/src/utils/macros.jl#L48-L56)) does at least *attempt* to restore the previous value, but it too has no `try/finally`, so the same failure mode applies there. Additionally, `@blas_1`'s own docstring claims to "temporarily" set threads to 1, but it never restores anything at all — the name/docstring promise a save/restore that doesn't exist.
- **Concurrency race on global BLAS thread count.** `BLAS.set_num_threads` is process-global, not thread-local. `@blas_1`/`@blas_multi_then_1` are called from `solve`/`solve_vect` in [dlp.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/dlp.jl#L377-L394) and [cfie.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/cfie.jl#L435-L452), and these `solve` calls happen underneath `compute_spectrum(solver::BeynSolver, ...)`'s per-window loop, which is explicitly threaded via `@use_threads multithreading=multithreaded_windows for i in 1:nw` ([spectralutils.jl#L399](../../../.julia/dev/QuantumBilliards.jl/src/spectra/spectralutils.jl#L399)). Two windows running concurrently can each call `@blas_1`/`@blas_multi_then_1` at the same time and stomp on each other's global thread-count setting mid-flight — a genuine, not-hypothetical data race given the confirmed threaded call path.
- `@blas_multi`/`@blas_multi_then_1` **ignore the caller's `multithreaded` flag entirely** — both call sites ([decompositionmethod.jl#L300](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/decompositionmethod.jl#L300), [verginisaraceno.jl#L197](../../../.julia/dev/QuantumBilliards.jl/src/solvers/acceleratedmethods/verginisaraceno.jl#L197), [dlp.jl#L380](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/dlp.jl#L380), [cfie.jl#L438](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/cfie.jl#L438)) hardcode `MAX_BLAS_THREADS` unconditionally, so calling `solve(...; multithreaded=false)` still lets BLAS spawn up to `Sys.CPU_THREADS` internal threads — exactly the "silent thread-count mismatch" this audit step was asked to check for.
- `@use_threads` itself ([macros.jl#L14-L40](../../../.julia/dev/QuantumBilliards.jl/src/utils/macros.jl#L14-L40)) handles the `multithreading=false`/runtime-value paths correctly and its `esc()` usage is sound (no hygiene issues found).

## Consolidation opportunities
- `utils/geometryutils.jl` — `angle(a, b) = atan(norm(cross(a,b)),dot(a,b))` is a **byte-for-byte duplicate** of `BilliardGeometry.jl`'s own `angle(a,b) = atan(norm(cross(a,b)),dot(a,b))` ([BilliardGeometry.jl/src/geometry/utils.jl#L97](../../../.julia/dev/BilliardGeometry.jl/src/geometry/utils.jl#L97)). `BilliardGeometry.jl` doesn't export `angle`, which is presumably *why* `QuantumBilliards.jl` re-implements it rather than reusing it via `using BilliardGeometry`. Flag only (cross-package design question, matches the earlier `bg-01` finding that `angle` legitimately extends `Base.angle`): either export `angle` from `BilliardGeometry.jl` and drop the duplicate here, or keep both but note the duplication explicitly as intentional decoupling.
- `utils/typeutils.jl`'s `set_precision` has no direct overlap with a `Base`/`StaticArrays` builtin worth consolidating — it's deliberately a coarser, hand-tuned tolerance than `Base.eps(T)`, not an accidental reimplementation. (See Unstable APIs above for its real weakness: the `Float32`-only special case.)
- No other builtin-vs-utility overlap found in `coordinatesystems.jl`/`billiardutils.jl`/`macros.jl`.
