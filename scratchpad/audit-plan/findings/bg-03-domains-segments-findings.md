## 3. Missing implementations

- **`reset_ids!` is a complete no-op — confirmed by direct execution.** ([compositedomains.jl#L13-L17](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/domains/compositedomains.jl#L13-L17)):
  ```julia
  function reset_ids!(domain::AbsCompositeDomain)
      for (i, sd)  in enumerate(domain.subdomains)
          @set sd.id = i
      end
  end
  ```
  `@set sd.id = i` (Accessors.jl) returns a **new** immutable value but it is never assigned back into `domain.subdomains[i]` nor returned — the loop body's result is discarded every iteration. Verified empirically: constructing a `CompositeDomain` with subdomain ids `[5,7]` and calling `reset_ids!` leaves the ids as `[5,7]`, unchanged. Despite its `!`-suffix (implying mutation) and docstring comment ("generate new ids…"), it does nothing. **New finding**, not tracked anywhere.
- **`Polygon`/`CircleWedge` have no degenerate-input guards.** [polygons.jl#L9-L22](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/domains/polygons.jl#L9-L22): a 1- or 2-corner input silently builds a "polygon" with a zero-length edge (`CircularArray` wraps the single point onto itself) and an `angle(...)` computation over a zero vector, which will silently yield `NaN`/`0` rather than erroring. **New finding.**
- **`MultiplyConnectedDomain` doesn't guard against `hole_curve_groups = []`.** ([multiplyconnecteddomains.jl#L34-L38](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/domains/multiplyconnecteddomains.jl#L34-L38)): calling it with an empty hole-group vector silently produces a `genus == 0` `MultiplyConnectedDomain` that is behaviorally identical to a plain `SimpleDomain` but under the "multiply connected" type name — a degenerate, single-component "multiply connected domain" is representable and not rejected. Low severity (matches the plan's stated design of deriving `genus` from `length(hole_curve_groups)`), but worth flagging per the checklist's explicit callout.

## 4. Unstable APIs

- **`LineSegment`/`CircleSegment` constructors do NOT `promote_type`, unlike `FourierCoeffPolarSegment`/`PolarSegment` — confirmed by direct execution, a real regression risk vs. the fix already applied to the polar types.**
  - [linesegment.jl#L19-L25](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/linesegment.jl#L19-L25): `pt0`/`pt1` are each cast via their *own* `eltype`, with no common-`T` promotion.
  - [circlesegment.jl#L19-L28](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/circlesegment.jl#L19-L28): `R`, `arc_angle`, `shift_angle`, `center` are passed straight through with no `promote_type`.
  - Verified directly:
    ```
    LineSegment([0.0,0.0], SVector{2,Float32}(1f0,1f0))   → MethodError
    CircleSegment(1, 2.0*pi, 0.0, [0.0,0.0])              → MethodError (Int R)
    CircleSegment(1.0f0, 2.0*pi, 0.0, [0.0,0.0])          → MethodError (Float32/Float64 mix)
    ```
  - By contrast, `FourierCoeffPolarSegment`/`PolarSegment` ([polarcurves.jl#L24-L26](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/polarcurves.jl#L24-L26), [polarcurves.jl#L57-L59](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/polarcurves.jl#L57-L59)) both correctly call `promote_type(...)` — this was the exact Gap 5 fix from [geometry-audit-10.9.md](/home/clozej/.julia/dev/BilliardGeometry.jl/memories/repo/geometry-audit-10.9.md), but it was never generalized to their sibling `LineSegment`/`CircleSegment` types, so the inconsistency the checklist asks about is real and currently unaddressed. **New finding, not tracked in any memory file.** Currently unexercised in practice only because every billiard call site in `billiards/*.jl` explicitly casts arguments to a single `T` before calling (e.g. `T(2*pi)`, `zero(T)`) — but the constructors themselves offer no such safety net for any other caller (e.g. `CircleWedge`, `Polygon`, or a user script), unlike the polar segment types.
  - `Polygon`'s constructor ([polygons.jl#L11](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/domains/polygons.jl#L11)) has the same weakness: `type = eltype(corners[1])` uses only the *first* corner's element type, silently dropping/erroring on a mixed-type corner list instead of promoting.
- **Gratuitous signature inconsistency (checklist-requested comparison):** `LineSegment`/`CircleSegment` take their geometric parameters (`pt0,pt1` / `R,arc_angle,shift_angle,center`) **positionally**, while `FourierCoeffPolarSegment`/`PolarSegment` take `R`/`arc_angle`/`shift_angle`/`center` **all as keywords with defaults** ([polarcurves.jl#L20](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/polarcurves.jl#L20), [polarcurves.jl#L53](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/polarcurves.jl#L53)). `CircleSegment` additionally offers two positional forms (`center::SVector` vs. separate `x0,y0`, [circlesegment.jl#L19](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/circlesegment.jl#L19) / [circlesegment.jl#L25](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/circlesegment.jl#L25)) that `LineSegment` has no equivalent of. **New finding** — not a bug, but a real cross-type inconsistency exactly matching the checklist's callout; minor keyword ordering also differs (`bc` precedes `orientation` in Line/Circle, follows it in the polar types).

## 5. Vulnerabilities

- **No radius/geometry validation anywhere in `circular.jl`/`circlesegment.jl`/`polygons.jl`.** Negative or zero `R` is accepted silently by `CircleSegment`/`CircleWedge`/`FourierCoeffPolarSegment`/`PolarSegment` constructors — geometrically meaningless curves are constructed without error. **New finding**, low-severity (consistent with the rest of the package's general lack of input validation, not a specific regression), but explicitly requested by the checklist.
- **`PolarSegment`'s `ForwardDiff`-based derivative path does silently propagate NaN/Inf for a bad `r_func`, confirmed by design inspection.** `tangent`/`tangent_2` for `PolarSegment` ([curvederivatives.jl#L86-L96](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/curvederivatives.jl#L86-L96)) call nested `ForwardDiff.derivative` on `curve(polar_curve, t)`; if the user's `r_func` is non-differentiable, discontinuous, or returns `NaN`/`Inf` near `t`, `ForwardDiff` will silently return `NaN` rather than throwing — there is no domain check (e.g. finiteness assertion) anywhere in the polar segment code path. **New finding.** This matches ordinary `ForwardDiff` semantics elsewhere in the package (not a novel weakness introduced here), but is worth flagging since arbitrary user closures are a new, wider attack surface for bad input compared to the fixed-form `FourierCoeffPolarSegment`.
- `reset_ids!`'s no-op (§3) is not itself a security issue, but is a correctness footgun if a future composite-domain constructor comes to rely on it to de-duplicate ids.

  ```julia
  line2 = LineSegment(center, pt0; bc = bc = bcs[3], domain_id=id, segment_id=3)
  ```

  `bc = bc = bcs[3]` parses as `bc = (bc = bcs[3])`: it evaluates fine at runtime (the keyword `bc` ends up correctly set to `bcs[3]`, confirmed by inspection of Julia's assignment semantics — right-associative `=` returns the assigned value) but has the unintended side effect of creating a stray local variable `bc` in `CircleWedge`'s constructor scope, and is a clear leftover editing mistake (compare to the correct `bc = bcs[1]`/`bc = bcs[2]` on the two preceding lines). **New finding** — no functional bug today (given `CircleWedge` is otherwise dead code per §1), but should be cleaned to `bc = bcs[3]`.
