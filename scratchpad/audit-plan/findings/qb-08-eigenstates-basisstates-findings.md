# Step qb-08: Eigenstates & basis states — Findings

**Scope**: [states/eigenstates.jl](../../../../.julia/dev/QuantumBilliards.jl/src/states/eigenstates.jl), [states/basisstates.jl](../../../../.julia/dev/QuantumBilliards.jl/src/states/basisstates.jl), cross-checked against `abstracttypes.jl`'s `AbsState` contract, qb-01's export audit, qb-04's `BIMEigenstate`-population findings, and the two migration-plan docs. Read-only — no files edited. Downstream consumers (`states/boundaryfunctions.jl`, `states/wavefunctions.jl`, `states/husimifunctions.jl`, `QBPlotting.jl`, `QCPlotting.jl`) were only grepped for field-usage evidence, not analyzed in depth (that's qb-09's job).

## 1. Dead code
- **`dim::Int64` is a write-only field on all three types** (`BasisEigenstate`, `BasisState`, `BIMEigenstate`). Every constructor computes and stores it (`length(vec)`), but a workspace-wide search (including `QBPlotting.jl`/`QCPlotting.jl`) found zero reads of `state.dim` anywhere — every `.dim` access in the codebase is `basis.dim` (a different object). This is genuinely dead per-instance data, not just an internal convenience.
- **`BasisState`'s `k_basis` and `eps` fields are also dead.** The only functions reading `.k_basis`/`.eps` are the generic `S<:AbsState` methods in [wavefunctions.jl](../../../../.julia/dev/QuantumBilliards.jl/src/states/wavefunctions.jl#L186) and [boundaryfunctions.jl](../../../../.julia/dev/QuantumBilliards.jl/src/states/boundaryfunctions.jl#L117), both of which also read `state.billiard` — a field `BasisState` doesn't have, so those generic methods are never dispatched to for a `BasisState` (its own `wavefunction(state::BasisState; ...)` override reads only `state.k`, `state.basis`, `state.idx`). So 3 of `BasisState`'s 7 fields (`k_basis`, `dim`, `eps`) are stored but never consumed by any reachable code path.
- **`BIMEigenstate`'s `k_basis` and `eps` fields are similarly dead** for the same structural reason (no `.basis` field, so the generic `AbsState` methods that read `k_basis`/`eps` can never be dispatched to it — its own `boundary_function`/`momentum_function`/`husimi_function`/`wavefunction` overrides never reference them). `k_basis` is documented as "no separate basis-evaluation wavenumber for BIM solvers" (i.e. kept only for structural `AbsState`-shape parity), which is a defensible design choice — but `eps` has no such justification and looks like an unintentional carry-over from copying `BasisEigenstate`'s shape.
- No constructor overload is unreachable: `BasisEigenstate`'s two explicit constructors (6-arg, 7-arg) each have a live call site in `compute_eigenstate`; `BIMEigenstate`'s single 8-arg constructor is called from `compute_eigenstate(::SweepBIMSolver,...)`; `BasisState`'s 3-arg constructor has no call site *within* `QuantumBilliards.jl` itself, but it is exported and its docstring frames it as an external plotting/inspection convenience — no evidence it's actually dead, just unused internally (worth confirming with the user/QBPlotting.jl maintainers if this is still exercised there).

## 2. Missing wiring
- `BasisEigenstate`, `BasisState`, `compute_eigenstate`, `BIMEigenstate` are **all correctly exported** ([QuantumBilliards.jl#L77-L79](../../../../.julia/dev/QuantumBilliards.jl/src/QuantumBilliards.jl#L77-L79)) — no drift from qb-01's baseline.
- `AbsState` itself is **still not exported**, confirmed unchanged from qb-01's finding (not re-analyzed here, just verified still true — not stale).

## 3. Missing implementations
- **`compute_psi(state::S, x_grid, y_grid; ...) where {S<:AbsState}` has no `BIMEigenstate` override**, and none is needed structurally *if* callers only ever go through `wavefunction` — but `compute_psi` is independently exported and documented with the `S<:AbsState` bound implying universal applicability. Calling `compute_psi(bim_state, x_grid, y_grid)` directly will throw `type BIMEigenstate has no field basis` (its body does `basis=state.basis`, `eps=state.eps` — `BIMEigenstate` has neither field). `wavefunction(state::BIMEigenstate; ...)` deliberately bypasses `compute_psi` entirely with its own grid+`ϕ_slp` implementation, so this gap is silent unless a caller/test/plotting script calls `compute_psi` directly on a BIM state (existing test/references to `compute_psi` are all against `BasisEigenstate`s, so this hasn't been exercised yet). Flag as a genuine, currently-latent implementation gap.
- **`AbsState`'s docstring API list** (`boundary_function`, `momentum_function`, `wavefunction`, `husimi_function` — "the following functions can be evaluated for any `AbsState`") **is not actually satisfiable by `BasisState`**: `BasisState` has no `billiard`/`solver`/`ten` fields, so the generic `S<:AbsState` methods for `boundary_function`/`momentum_function`/`husimi_function` would all throw a field-access error if invoked on it. `basisstates.jl`'s own docstring is accurate here (its `## API` section correctly lists only `wavefunction`) — the mismatch is entirely in `abstracttypes.jl`'s `AbsState` docstring overpromising a contract that one of its three concrete subtypes doesn't (and isn't meant to) fulfill. Suggest narrowing `AbsState`'s docstring wording (e.g. "most `AbsState` subtypes support..., see each concrete type's own `## API` list") rather than implying a uniform contract.
- All four `AbsState`-documented functions **are** correctly implemented (via specific overrides) for both `BasisEigenstate` and `BIMEigenstate` — confirmed by reading every dispatch pair in `boundaryfunctions.jl`/`wavefunctions.jl`/`husimifunctions.jl`.

## 4. Unstable APIs
- **`BIMEigenstate{K,T,S,Bi}`'s four type parameters are always concretely inferred** — confirmed by tracing the single constructor: `K = eltype(vec)` (concrete, since `vec::Vector{K}` from `solve_state`), `S`/`Bi` are `typeof(solver)`/`typeof(billiard)` at the call site (always concrete for a concrete instance, regardless of the static type of the variable holding them — same non-issue already established for `Sy`-style params in qb-04), and `T` is derived from `ten`/`eps`/`bnd_norm`/`pts::BoundaryPoints{T}` all needing to agree. **However**, this last point is a latent fragility, not a guarantee: the struct's default positional constructor requires `ten`, `eps`, and `pts`'s own `T` to all be the *same* concrete type — if `solve_state` ever returned a `ten` with a different real type than `real(eltype(vec))` (e.g. a mixed-precision solve), construction would fail with an opaque `MethodError` rather than a clear message. Not currently triggered (not a bug today), but worth a one-line internal assertion/comment if this code is touched again.
- **`BasisEigenstate`/`BIMEigenstate` filtering-`eps` type inconsistency, confirmed and extended from qb-01's flag**: `BasisEigenstate` uses `set_precision(vec[1])` while `BIMEigenstate` uses `set_precision(real(vec[1]))`. Tracing `set_precision`'s fallback (`convert(t, 1e-16)` for any non-`Float32` type, per qb-01) through to a **hypothetical complex `vec`**: `set_precision(vec[1])` on a `ComplexF64` would return a *complex*-typed `eps`, which would then fail with `MethodError: no method matching isless(::ComplexF64, ::Float64)` the moment `abs(vec[i]) > eps` is evaluated (e.g. in `compute_psi`'s memory-fallback branch). This is currently unreachable only because every concrete basis (`RealPlaneWaves`, `CornerAdaptedFourierBessel`) produces real-valued eigenvectors from a real generalized eigenproblem — confirming qb-01's "currently harmless" framing with the concrete failure mode. Still worth fixing for robustness (mirror `BIMEigenstate`'s `real(vec[1])`) since the `eltype(vec) <: Real` branch structure elsewhere in the same constructor clearly anticipates a complex `vec` as a possibility.
- `BasisState{K,T,Ba}`'s two type parameters `K` (for `k`/`k_basis`) and `T` (for `vec`/`eps`) are **always identical in practice** — the sole constructor sets `typ = typeof(k)` and uses it for both `vec`'s eltype and `eps`, so `K == T` always. Not a bug (no code path relies on them differing), just worth noting the parameterization looks more general than it's ever actually used — unlike `BasisEigenstate`/`BIMEigenstate` where `K` (possibly complex `vec` eltype) and `T` (always-real tension/eps type) are genuinely allowed to differ.

## 5. Vulnerabilities
- **No partially-constructed-state escape is possible** — all three types are immutable `struct`s with a single atomic positional constructor; every field must be supplied before the value exists, so `vec`/`ten`/`bnd_norm` can never be read via a half-built instance. This checklist concern does not apply.
- **`compute_eigenstate(solver::AcceleratedBasisSolver, ...)`** ([eigenstates.jl#L194](../../../../.julia/dev/QuantumBilliards.jl/src/states/eigenstates.jl#L194)) calls `idx = findmin(abs.(ks.-k))[2]` on the array `ks` returned by `solve_vectors`. If `solve_vectors` returns an **empty** `ks` (no candidate eigenvalue located within `dk` of `k` — plausible for a `dk` window with no billiard eigenstate in it), `findmin` on an empty vector throws `ArgumentError: collection must be non-empty` — an unclear, unactionable error for what is really a "no eigenstate found in this window, try a larger `dk`" user-facing condition. Same shape of issue does not apply to `compute_eigenstate(::AcceleratedBIMSolver,...)`, since `solve_wavenumber` returns a single root, not an array to search.
- **No unchecked non-empty assumption on `pts`/`u` was found to be exercised in practice** — `evaluate_points`'s own `min_pts`/`min_dim` floors (audited in qb-04/qb-05) already guarantee non-trivial discretizations reach `BIMEigenstate`/`BasisEigenstate`, so this is a theoretical rather than reproducible concern; flagged only because the checklist explicitly asked for it.

## 6. Consolidation opportunities
- **The negligible-coefficient filtering block is duplicated verbatim three times** — in both `BasisEigenstate` constructors ([eigenstates.jl#L74-L79](../../../../.julia/dev/QuantumBilliards.jl/src/states/eigenstates.jl#L74-L79), [#L110-L115](../../../../.julia/dev/QuantumBilliards.jl/src/states/eigenstates.jl#L110-L115)) and in `BIMEigenstate`'s constructor ([#L280-L285](../../../../.julia/dev/QuantumBilliards.jl/src/states/eigenstates.jl#L280-L285)):
  ```julia
  if eltype(vec) <: Real
      filtered_vec = eltype(vec).([abs(v)>eps ? v : zero(vec[1]) for v in vec])
  else
      filtered_vec = vec
  end
  ```
  differing only in how `eps` itself is computed beforehand. A single private helper (e.g. `_filter_negligible_coefficients(vec, eps)`) in `eigenstates.jl` would remove the triplication with zero behavior change, and would also be the natural place to fix the `set_precision(vec[1])` vs `set_precision(real(vec[1]))` inconsistency noted in §4 (by making the helper itself always take a real `eps` and compute it consistently, e.g. `set_precision(real(vec[1]))` in one place instead of two divergent call sites).
- No other meaningful duplication found between `BasisEigenstate`/`BasisState`/`BIMEigenstate`'s own bodies — the two `BasisEigenstate` constructors' simpler case is not delegated to the more general one (both independently call the same filtering logic and the default 9-arg constructor), which is a smaller instance of the same duplication above, not a separate issue.
