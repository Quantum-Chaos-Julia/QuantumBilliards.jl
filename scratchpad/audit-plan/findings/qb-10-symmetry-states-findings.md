## 4. Unstable APIs

- **`symmetry_sector(billiard, choices::Pair...)` validates unknown generator types but silently accepts duplicates.** [symmetrysector.jl:72-79](/home/clozej/.julia/dev/QuantumBilliards.jl/src/states/symmetry/symmetrysector.jl#L72-L79): an unregistered `GenType` correctly throws (`isempty(matches) && throw(ArgumentError(...))`). But nothing prevents the same `GenType` appearing twice in `choices` with different values, e.g. `symmetry_sector(b, XAxisReflection=>1, XAxisReflection=>-1)` — the `Dict` assignment `characters[sym.sym_id] = _sector_character(sym, val)` simply lets the second pair silently overwrite the first with no error or warning. This is a real, easy-to-hit caller mistake (e.g. accidental duplicate keyword-style argument in a long call) that resolves to "whichever pair came last," not a validated choice.
- `_sector_character(::AbsReflection, val::Integer)` dispatches generically on the abstract `AbsReflection` supertype rather than per concrete type — appropriate here (every reflection subtype shares the same `±1` validation), not a weakness.
- No `Any`-typed fields/arguments found in either file; `SymmetrySector{Bi<:BilliardGeometry.AbsBilliard}` correctly parameterizes on the concrete billiard type.

## 5. Vulnerabilities

- **Headline finding: a `SymmetrySector` built against one billiard can be silently consumed against a *different* billiard whose registered `sym_id`s happen to coincide.** Since `sym_id`s are assigned purely by registration order within each billiard's own constructor (per [15-symmetry-representation-refactor.md](/home/clozej/Programs/QuantumBilliardsTests/scratchpad/migration-plan/15-symmetry-representation-refactor.md)'s `register_symmetries`), essentially *every* `D2_symmetry()`-based billiard (`RectangleBilliard`, `StadiumBilliard`, `CircleBilliard`, `EllipseBilliard`, `ProsenBilliard`) registers `YAxisReflection`/`XYAxisReflection`/`XAxisReflection` with the identical `sym_id`s `1,2,3` (per bg-02's confirmed catalogue). Concretely:
  ```julia
  sector = symmetry_sector(RectangleBilliard(1,1), XAxisReflection=>-1)
  basis  = RealPlaneWaves(20, StadiumBilliard(0.5), sector)   # wrong billiard!
  ```
  succeeds silently — neither [realplanewaves.jl:225-230](/home/clozej/.julia/dev/QuantumBilliards.jl/src/basis/planewaves/realplanewaves.jl#L225-L230) nor `_resolve_bim_symmetry` ([symmetrysector.jl:114-117](/home/clozej/.julia/dev/QuantumBilliards.jl/src/states/symmetry/symmetrysector.jl#L114-L117)) ever check `billiard === sector.billiard` (or an equivalent identity/equality check) — they only check "does *this* billiard argument happen to register a symmetry with *this* `sym_id` integer" via `BilliardGeometry.symmetry_of`, which is a materially weaker condition than "is this the same billiard the sector was built for." This directly contradicts the `_resolve_bim_symmetry` docstring's own explicit claim ("this is what closes the 'sector built against the wrong billiard' gap") — that claim is only true for the *same-object* case; it is false for the cross-billiard, same-`sym_id`-shape case, which is the common case in this ecosystem, not a rare edge case. This is precisely bg-02's Gap 6 (no `SymmetryWall`/`billiard.symmetries`/solver-sector consistency check) — confirmed here to be the layer where that check is missing, and worse than "silently falls back to the trivial representation": it silently resolves to a *wrong but non-trivial* representation with no indication anything is amiss.
  - **Suggested fix** (not applied, per read-only scope): add `billiard === sector.billiard || throw(ArgumentError("SymmetrySector was built against a different billiard"))` at the top of both consumers, using the already-stored (currently dead, per §1) `sector.billiard` field — this would also retroactively resolve the §1 dead-field finding.
- The duplicate-`GenType`-pair gap (§4) is a related, lower-severity vulnerability: a mistyped call silently keeps only the last-specified character with no error.
- No other silent-trivial-representation fallback found — `symmetry_of`/`symmetry_sector`'s "unknown `sym_id`/`GenType`" paths both throw loudly, consistent with bg-02's finding that this ecosystem generally fails loud rather than silently substituting `nothing`.

## 6. Consolidation opportunities

- **`reflections.jl` re-derives `BilliardGeometry`'s own orientation-reversal trait by hand instead of calling it.** BilliardGeometry.jl already has `_orientation_reversing(sym)` ([fullboundary.jl:30-35](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/fullboundary.jl#L30-L35): `true` for `XAxisReflection`/`YAxisReflection`/`DiagonalReflection`/`AntiDiagonalReflection`, `false` for `XYAxisReflection`/`NFoldRotation`), used by its own `apply_symmetry_pb`/`full_boundary`. `reflections.jl`'s `apply_symmetries_to_boundary_points` ([reflections.jl:224-226](/home/clozej/.julia/dev/QuantumBilliards.jl/src/states/symmetry/reflections.jl#L224-L226)) hardcodes the identical fact as literal `true`/`false` arguments to `push_reflection!` at each call site (`push_reflection!(get_sym(YAxisReflection), true)`, `push_reflection!(get_sym(XYAxisReflection), false)`, `push_reflection!(get_sym(XAxisReflection), true)`), and `apply_symmetries_to_boundary_function`/`apply_symmetries_to_wavefunction` encode the same fact again via which branches call `reverse(...)`. This is genuine duplicated reflection-formula logic across the package boundary — `_orientation_reversing` is unexported/private today, so the fix is either (a) export it from `BilliardGeometry.jl` and call `BilliardGeometry._orientation_reversing(sym)` (or an exported equivalent) from `reflections.jl` instead of the hardcoded booleans, or (b) accept the duplication as intentional decoupling if the two packages are meant to never share private internals — but as-is it's an un-flagged, silent duplication that would drift if either side's convention ever changed (e.g. a future `DiagonalReflection`-based billiard).
- **Intra-file duplication within `reflections.jl` itself**: all three functions (`apply_symmetries_to_wavefunction`, `apply_symmetries_to_boundary_function`, `apply_symmetries_to_boundary_points`) independently re-implement the same `has_x = any(s -> s isa XAxisReflection, symmetries)` / `has_y = any(...)` / four-way branch (`has_x&&has_y` / `has_y` / `has_x` / else) skeleton, differing only in what's being reflected (grid array, boundary vector, point/normal/arc-length triple). A shared internal dispatch helper (e.g. a small `_reflection_case(symmetries)` trait, or restructuring the three functions to share one "walk the applicable reflections in canonical order" driver that takes a per-element reflect/append callback) would remove this 3x repetition — a real, in-scope consolidation opportunity, though the three bodies operate on different data shapes so full unification has diminishing returns; a partial shared helper for `has_x`/`has_y`/`get_qnum`/`get_sym` lookup would still help.
- `apply_symmetries_to_boundary_points` does correctly reuse `BilliardGeometry.apply_symmetry(sym, bxy)`/`apply_symmetry(sym, bn)` for the actual geometric point/normal transforms — this part is properly delegated to the geometry package, not duplicated. Only the orientation/ordering bookkeeping (above) is re-derived rather than reused.
