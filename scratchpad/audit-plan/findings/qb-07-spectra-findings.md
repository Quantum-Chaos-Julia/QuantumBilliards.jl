## 5. Vulnerabilities

- **`merge_spectra` is a broken, exported public function** (restated from §3 — the most severe finding): any external caller following the export list would hit an immediate `UndefVarError`. Recommend either (a) implementing `interval`/`intersect_interval`/`in_interval` (or swapping to `IntervalArithmetic`'s actual API / plain scalar comparisons, since the logic only needs "is k inside `[lo,hi]`" and "intersect two `[lo,hi]` ranges" — trivial without a dependency), or (b) removing `merge_spectra` from the export list and the file entirely, since it has zero call sites (§1) and its functionality (merging two already-computed `SpectralData` sets by wavenumber-overlap) is not otherwise exercised by `compute_spectrum`'s own window-merging path (which uses `overlap_and_merge!`/`overlap_and_merge_ebim!` directly on raw vectors, not `SpectralData` objects).
- **`_finalize_spectrum`'s "workers write disjoint slots, one thread finalizes" docstring claim does not match any of its 4 actual call sites.** Traced each: `compute_spectrum(::AcceleratedBasisSolver,...)` ([L117-L131](../../../../.julia/dev/QuantumBilliards.jl/src/spectra/spectralutils.jl#L117-L131)) accumulates via a strictly sequential `while` loop; `compute_spectrum(::BeynSolver,...)` ([L390-L411](../../../../.julia/dev/QuantumBilliards.jl/src/spectra/spectralutils.jl#L390-L411)) has exactly one `@use_threads` region (L399), but it writes only into `all_pts[i]` (boundary-point discretizations) — the subsequent loop that actually fills `ks_win[i]`/`tens_win[i]` (the arrays that feed `_finalize_spectrum` after `reduce(vcat,...)`) is a plain sequential `@inbounds for` (L403-L406), not threaded; `compute_spectrum(::ExpandedBIMSolver,...)` ([L483-L538](../../../../.julia/dev/QuantumBilliards.jl/src/spectra/spectralutils.jl#L483-L538)) fills `ks_corr`/`tens_corr` via a plain sequential segment loop; `compute_spectrum_refined` explicitly documents its seed-refinement loop as deliberately *not* threaded (to avoid nesting). So in every current caller, `_finalize_spectrum`'s inputs are produced by a single thread — the docstring's specific claim ("this is how e.g. `BeynSolver`/`ExpandedBIMSolver` already operate") is not accurate as literally stated; the only actual threaded region in this file (Beyn's boundary-point evaluation) writes to a *different* array than the one `_finalize_spectrum` ever touches, and fully completes before the sequential `solve` loop begins. **No live race exists** (good news — the function is safe), but the rationale in the docstring over-describes a "disjoint-slots" pattern that isn't the actual reason it's safe today; the real reason is simpler (nothing writes to `ks`/`ts`/`control` concurrently at all, currently). Worth a docstring correction if this file is revisited, but not a functional bug.
- **`overlap_and_merge!`'s tail-append logic relies on an unenforced invariant.** ([spectralutils.jl#L52-L94](../../../../.julia/dev/QuantumBilliards.jl/src/spectra/spectralutils.jl#L52-L94)): `fl = findlast(idx_r); idx_last = fl+1; append!(k_left, k_right[idx_last:end])` is only correct if `idx_r` (the boolean overlap-window mask over `k_right`) forms a **contiguous prefix** of `k_right` — i.e., `k_right` must be sorted ascending and the only overlap-eligible points must be the leading ones. This holds given the current call site's window geometry (`k_right` is a fresh, presumably-sorted `solve_spectrum` result, and the overlap zone `[kl-tol,kr+tol]` only ever brackets its low end because `kr=k0` is exactly `k_right`'s window center), but the invariant is never asserted/checked in `overlap_and_merge!` itself. If `k_right` were ever non-sorted, or contained a spurious matched point past a later unmatched one, indices between the last-true position and any earlier gaps would be silently dropped from `k_left` rather than either merged or appended — a genuine, if currently latent, silent-eigenvalue-loss footgun matching the checklist's specific concern. Low practical severity today (mitigated by `solve_spectrum` always returning sorted output, confirmed structurally, not by an explicit check here), but worth an `@assert issorted(k_right)` or equivalent guard if this function is ever touched again.
- **`overlap_and_merge_ebim!`'s adaptive clustering can merge genuinely distinct, closely-spaced roots** — already flagged in detail by qb-05's findings (same function, same file); re-confirmed by direct reading here: the `clamp`-style tolerance `min(tolmax, max(tol, spacing_frac*local_gap))` with defaults `tol=1e-5, tolmax=5e-3, spacing_frac=0.02` can exceed a true physical level spacing for near-degenerate/regular spectra, and the function keeps only the best-scoring representative per cluster with no way for a caller to inspect what was discarded (`control[i]` only records *that* a merge happened, not what was merged away). This is inherent to the design (not a coding bug) — restating qb-05's finding here since it's directly in this step's file scope.
- No `epsilon`/boundary-convention bug found in `overlap_and_merge!`'s window-boundary comparisons themselves (`k_left .> (kl-tol) .&& k_left .< (kr+tol)`) beyond the already-known Beyn contour-boundary double-counting issue qb-05 flagged (that lives in `_beyn_solve_core`, out of this step's file scope, not re-analyzed here).

## 6. Consolidation opportunities

- **`overlap_and_merge!` and `overlap_and_merge_ebim!` should *not* be unified** — confirmed by direct reading, matching the design record in [09.5-compute-spectrum.md](/home/clozej/Programs/QuantumBilliardsTests/scratchpad/migration-plan/09.5-compute-spectrum.md): `overlap_and_merge!` resolves overlap between two *explicitly-bounded, contiguous* windows using error-bar-matched wavenumber pairing (`match_wavenumbers`/`is_equal`) restricted to a known `[kl,kr]` boundary zone; `overlap_and_merge_ebim!` clusters an *unbounded, densely-overlapping* set of trial roots by adaptive local spacing with no window-boundary concept at all. They share no common loop structure, no common tolerance semantics (fixed vs. spacing-adaptive), and operate on structurally different inputs (`overlap_and_merge!` takes two already-separate window results plus explicit `kl,kr`; `overlap_and_merge_ebim!` takes an accumulator and one new point at a time with no window bounds). Forcing a shared helper would only reintroduce a parameter-laden branch — both functions are correctly kept distinct.
- `is_equal`/`match_wavenumbers` are used only by `overlap_and_merge!` and `merge_spectra` — since `merge_spectra` is broken/dead (§1/§3), `match_wavenumbers`' only *live* caller is `overlap_and_merge!`. No consolidation action needed here, just noting the reduced live-usage surface once `merge_spectra` is addressed.
- No overlap found between `unfolding.jl`'s Weyl-law functions (`corner_correction`, `weyl_law`, `k_at_state`, `state_at_k`, `spectral_density`, `k_range_for_states`) and anything in `spectralutils.jl` — clean separation of concerns per the 12.5 design, nothing to merge.
