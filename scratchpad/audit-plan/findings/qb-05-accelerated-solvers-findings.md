## 4. Unstable APIs
- **`BeynSolver`/`ExpandedBIMSolver` constructor signatures are consistent** where they overlap: both share identical Chebyshev-keyword names/defaults (`use_chebyshev=true, n_panels_h=15000, M_h=5, n_panels_j=10000, M_j=5, cheb_config=nothing`), both derive `T=_bim_numeric_type(kernel)` and build a `ChebyshevConfig(T;...)` identically when `cheb_config===nothing`. `BeynSolver`'s extra `m,nq,r,svd_tol,res_tol,auto_discard_spurious` fields are algorithm-specific (contour planning/rank/residual), not a naming inconsistency.
- **Constructor does not fail fast when `use_chebyshev` (default `true`) is combined with a non-`Float64` kernel.** Neither `BeynSolver(...)` nor `ExpandedBIMSolver(...)` validates `T===Float64` at construction time even though `use_chebyshev` defaults to `true`; the error ("Chebyshev-accelerated ... evaluation currently requires a Float64 kernel ... Construct with use_chebyshev=false") only fires on the *first* `construct_matrices`/`solve` call. For a `Float32` `SweepBIMSolver` kernel, `BeynSolver(kernel)` succeeds silently and only errors deep inside a later sweep — a fail-fast check in both constructors (`T===Float64 || use_chebyshev || nothing` — i.e. error immediately if `use_chebyshev && T!==Float64`) would surface this at construction instead.
- `compute_spectrum`'s effectively-four (six, see item 3) dispatch variants **do share a consistent `SpectralData` return type** with no leftover bare-tuple/array variant — confirmed by direct reading, not just the 12.5 plan's own claim.
- `_beyn_solve_core`'s returned `tens` field is actually the raw nonlinear residual norm `‖A(λ)φ‖`, not a Vergini–Saraceno-style tension — this is consistent with `SpectralData`'s own docstring (`ten`: "tension (or tension-like quality measure)"), so not a bug, just worth noting it's a different physical quantity reused under the same field name across solver families (pre-existing, documented design choice from Step 9.5, not something to change here).

## 5. Vulnerabilities
- **Beyn contour-boundary double-counting, not just omission.** `compute_spectrum(solver::BeynSolver,...)`'s docstring ([spectralutils.jl](../../../../.julia/dev/QuantumBilliards.jl/src/spectra/spectralutils.jl)) explicitly acknowledges "a genuine root sitting exactly at a window boundary could in principle be found (or missed) by at most one neighboring window." Tracing the actual containment check in `_beyn_solve_core` — `abs(λ[j]-k0c)>Rc && continue` (i.e. **kept** when `abs(λ-k0)<=Rc`, inclusive) — combined with `plan_weyl_windows`' contiguous, touching windows (window *i*'s right edge `kR` equals window *i+1*'s left edge `kL`), means a root sitting exactly at a shared boundary is within `<=R` of **both** adjacent contour centers and would be kept by **both** windows. Since `compute_spectrum(::BeynSolver,...)` performs no overlap merge (by design, since windows are "disjoint"), such a root would appear **twice** in the final `SpectralData` rather than merely being missed — a sharper version of the checklist's "silently missing eigenvalues near the contour boundary" concern (duplication, not omission, and with no warning either way). Purely a floating-point-exact edge case in practice, but worth a `>=`/`<` boundary-convention fix or an explicit warning/dedup pass if ever revisited.
- **`overlap_and_merge_ebim!`'s adaptive clustering can merge genuinely distinct, closely-spaced levels.** Per checklist item 5: the merge tolerance is `clamp(spacing_frac*local_gap, tol, tolmax)` with defaults `spacing_frac=0.02, tol=1e-5, tolmax=5e-3`. For a regular (Poisson-statistics) billiard, or any spectrum with genuine level clustering/near-degeneracy (accidental degeneracies, symmetry-unresolved multiplets), two real, physically distinct roots can have a true gap smaller than this adaptive tolerance; the function then keeps only the single best-scoring representative (lowest `|Im k|` + tension) per cluster and silently discards the other — the `control` flag records that a merge happened, but nothing raises a warning or lets a caller inspect what was dropped. This is inherent to the clustering-by-proximity design (not a coding bug), but it is a real, not just theoretical, silent-data-loss vulnerability for irregular/near-integrable billiards, matching the checklist's framing exactly.
- **`BeynSolver`/`ExpandedBIMSolver` constructors defer the `T===Float64` Chebyshev-compatibility check to first use** (see Unstable APIs) — a construction-time footgun rather than a numerical-correctness one, but still a "should fail immediately, doesn't" gap.
- Everything already flagged generically by `qb-01`/`qb-03`/`qb-04` (the non-restoring, non-exception-safe `@blas_1`/`@blas_multi_then_1`/`@blas_multi` global-BLAS-thread-count race, and its ignoring of the caller's `multithreaded` flag) applies again here: `beyn.jl`'s LU/`ldiv!`/`svdvals`/`svd!`/`eigen!` calls and `ebim.jl`'s `eigen(A,dA)`/`eigen(A',dA')` calls are all additional `@blas_multi_then_1` call sites inheriting that same pre-existing weakness — not re-analyzed here, flagged for completeness only.

## 6. Consolidation opportunities
- **`_bim_numeric_type` is defined identically twice** — `_bim_numeric_type(::BeynSolver{T}) where {T} = T` ([beyn.jl#L90](../../../../.julia/dev/QuantumBilliards.jl/src/solvers/acceleratedmethods/beyn.jl#L90)) and `_bim_numeric_type(::ExpandedBIMSolver{T}) where {T} = T` ([ebim.jl#L64](../../../../.julia/dev/QuantumBilliards.jl/src/solvers/acceleratedmethods/ebim.jl#L64)). This **cannot** be trivially hoisted to one generic method on `AcceleratedBIMSolver` in `acceleratedmethods.jl`, because `abstract type AcceleratedBIMSolver <: AbsBIMSolver end` ([abstracttypes.jl](../../../../.julia/dev/QuantumBilliards.jl/src/abstracttypes.jl)) declares no type parameter — there is nothing to dispatch `{T}` against at the abstract level. Genuinely minor, structurally-forced duplication; flagging only for completeness, not recommending a change (would require adding a type parameter to the abstract type, a larger design change out of this step's scope).
- **No meaningful shared contour/window-planning logic exists between `beyn.jl` and `ebim.jl` to consolidate.** The two solvers use genuinely different windowing strategies by design (`BeynSolver`: Weyl-balanced disjoint contour disks via `plan_weyl_windows`/`beyn_disks_from_windows`, entirely in `beyn.jl`; `ExpandedBIMSolver`: an adaptive dense trial-`k` grid with segment-reuse of `evaluate_points`, implemented in `compute_spectrum(::ExpandedBIMSolver,...)` in `spectralutils.jl`, not in `ebim.jl` at all). There is no duplicated window-planning code between the two files as things stand — checklist item 6's premise does not hold for the current implementation.
- The `_dlp_kernel_entry_with_derivatives`/`_cfie_kernel_entry_with_derivatives` value/derivative algebra in `ebim.jl` structurally mirrors (but does not literally duplicate — it must recompute the same `h0,h1,j0,j1` intermediates to get all three of value/1st-deriv/2nd-deriv from one special-function evaluation) `_dlp_kernel_entry`/`_cfie_kernel_entry` in `dlp.jl`/`cfie.jl`. This is architecturally justified (computing derivatives requires the same intermediates as the value, so delegating to the value-only function and redoing the special-function calls would be strictly worse), not a genuine duplication to fix — noted only to avoid re-flagging what `qb-04` already correctly identified as a *different* real duplication (the value-only `_dlp_fredholm_full!`/`_cfie_fredholm_full!` pair in `dlp.jl`/`cfie.jl` itself, out of this step's scope).

## 8. Threading/BLAS
- **No nested threading found anywhere in this file set.** `BeynSolver.construct_matrices`'s per-contour-node loop is deliberately left single-threaded (explicitly documented reason: each node's own `construct_matrices(solver.kernel,...)` call already parallelizes its own O(N²) assembly via `multithreaded`, so threading the node loop too would nest `Threads.@threads`); the LU factorization/triangular-solve/moment-accumulation loops instead use multithreaded BLAS via `@blas_multi_then_1`, a single parallelism level.
- `compute_spectrum(solver::BeynSolver,...)`'s window loop ([spectralutils.jl](../../../../.julia/dev/QuantumBilliards.jl/src/spectra/spectralutils.jl), out of file scope but the consumer of `beyn.jl`) threads only the independent `evaluate_points` calls across windows (`multithreaded_windows`); the subsequent `solve` calls per window run in a strictly serial loop, so no nesting with `construct_matrices`'s own internal `multithreaded` parallelism.
- `ebim.jl`'s `_ebim_fredholm_full_with_derivatives!`/`_ebim_fredholm_reduced_with_derivatives!`/`_composite_fredholm_full_with_derivatives!`/`_composite_fredholm_reduced_with_derivatives!` all use exactly one `@use_threads` outer level with a plain `@inbounds` (unthreaded) inner loop — consistent single-parallel-level convention. The composite variants' outer `for a in 1:nc`/`for b in 1:nc` component loops are plain (unthreaded) `for` loops wrapping an inner `@use_threads` region — correct, since `nc` (connected boundary components) is always small, mirroring `qb-04`'s identical finding for `compositebim.jl`'s non-derivative assembly.
- No BLAS/LAPACK/KrylovKit calls occur *inside* any `@use_threads` region in these five files; all such calls (`lu!`, `ldiv!`, `svdvals`, `svd!`, `eigen!`, `eigen`) happen after assembly, each wrapped in `@blas_multi_then_1` per the existing (pre-flagged, see Vulnerabilities) convention — no new macro-usage mistake introduced in this file set.
- This confirms the checklist's specific concern ("classic place to accidentally nest threading if the inner kernel evaluation is itself parallelized") is **correctly avoided** in `beyn.jl`, not merely undetected — the avoidance is explicit and documented in the `construct_matrices` docstring itself.
