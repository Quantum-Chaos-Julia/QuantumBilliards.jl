## 4. Unstable APIs
- **`boundary_limits`** ([wavefunctions.jl#L69-L70](../../../../.julia/dev/QuantumBilliards.jl/src/states/wavefunctions.jl#L69-L70)): `x_bnd = Vector{Any}(); y_bnd = Vector{Any}()` — a genuine `Any`-typed container, directly against the package's stated type-stability convention. Every curve's sampled points are boxed through `append!` into an abstractly-typed vector before `extrema` is taken. Called once per `wavefunction`/`boundary_function` reconstruction (not a hot inner loop), so the perf impact is small, but it's an unambiguous, easy-to-fix violation (e.g. `Vector{Float64}()`, or infer the concrete `T` from the first curve's own point type).
- **Inconsistent keyword surface across state types for `wavefunction`** vs. the other three functions: `boundary_function`/`momentum_function`/`husimi_function` deliberately keep an *identical* nominal keyword surface (`b`, `multithreaded`, plus `c`/`w`/`full_p` for Husimi) across `S<:AbsState` and `BIMEigenstate` — even accepting-but-ignoring `b`/`multithreaded` on the BIM side purely for polymorphic call-site compatibility (explicitly documented as such). `wavefunction` breaks this pattern: `wavefunction(state::BIMEigenstate;...)` adds `use_float32_bessel`, `use_chebyshev`, `cheb_npanels`, `cheb_M` and drops `fundamental_domain`/`memory_limit` entirely, while `wavefunction(state::S)` has no equivalent Chebyshev-toggle. A caller writing generic code against `AbsState` cannot pass one consistent keyword set to `wavefunction` the way it can for the other three — it must already know the concrete state type. Given item 3's finding, this divergence would only grow if/when `method=:green` support is added generically.
- No `Any`-typed struct fields in this scope (none of these three files define structs).

## 5. Vulnerabilities
- **Near-singular kernel evaluation close to the boundary is only guarded for exact coincidence.** `ϕ_slp` ([wavefunctions.jl#L131-L146](../../../../.julia/dev/QuantumBilliards.jl/src/states/wavefunctions.jl#L131-L146)) skips a source term only when `r2==0` exactly; for a grid evaluation point that is very close to (but not exactly on) a boundary node — entirely plausible for `inside_only=true`, since `is_inside` only excludes strictly-outside points — `Y₀(kr)` grows like the (mild, logarithmic) near-field singularity with no distance-based safeguard or adaptive local quadrature. This is a real accuracy risk for wavefunction reconstruction on grid points that land close to the boundary, not just a hypothetical.
- **The above risk is compounded, not mitigated, by the Chebyshev path.** `wavefunction(state::BIMEigenstate; use_chebyshev=true)` builds its plan with `rmin = hankel_z_chebyshev_cutoff/kT` ([wavefunctions.jl#L366](../../../../.julia/dev/QuantumBilliards.jl/src/states/wavefunctions.jl#L366)) but performs **no check** that every actually-evaluated `r` (source-to-grid-point distance) stays `≥ rmin`. Per qb-06's confirmed-still-open finding, `panel_t`/`_find_panel_uniform` silently **clamp** any out-of-range `r` to the first/last panel rather than erroring — so a grid point closer to the boundary than `rmin` would be silently, invisibly extrapolated instead of raising an error or falling back to direct `bessely0` evaluation. Cross-referencing this file's actual call site sharpens qb-06's generic finding into a concrete, reachable code path.
- **Correctness risk from divergent "is this grid uniform" criteria** (see also §6): `momentum_function(u,s,ds;...)` ([boundaryfunctions.jl#L282-L288](../../../../.julia/dev/QuantumBilliards.jl/src/states/boundaryfunctions.jl#L282-L288)) decides to take the fast FFT shortcut based on **`s`-spacing uniformity alone** — it never checks `ds`. The fast path (`momentum_function(u,s)`, a plain `rfft`) implicitly assumes the physical quadrature weight is constant (`ds = L/N`); if a boundary discretization ever produced arc-length samples that are (near-)evenly spaced while their quadrature weights are not (not proven to occur today, but structurally possible for a composite curve with different local parametrizations), this would silently produce a numerically wrong momentum spectrum. This is exactly the class of bug migration-plan 05.6 already found and fixed for `husimi_function`'s analogous check (`_bim_boundary_uniformly_spaced`, which checks **both** `s` and `ds`) — but that fix was not mirrored into `momentum_function`'s independent uniformity check.
- Husimi windowed-quadrature edge handling (`searchsortedfirst`/`searchsortedlast` in the general kernel, husimifunctions.jl) was specifically re-verified: the periodic-window centering fix from 05.6 (`q=qs[iq]` directly, not `qs[iq]+L`) is in place, guaranteeing a `≥L` margin on both sides for any `qs[iq]∈[0,L)`; `W = max(0, hi-lo+1)` correctly handles an empty window with no crash. **No residual off-by-one/wraparound bug found** — the fix holds up under this independent re-read.

## 6. Consolidation opportunities
- **New, concrete**: `momentum_function(u,s,ds;...)`'s uniform-grid detector ([boundaryfunctions.jl#L283-L284](../../../../.julia/dev/QuantumBilliards.jl/src/states/boundaryfunctions.jl#L283-L284)) and husimifunctions.jl's `_bim_boundary_uniformly_spaced` are two independently-written, near-duplicate "is this arc-length grid uniform" checks with **different criteria** (the former checks only `s`; the latter checks both `s` and `ds`) and different tolerance formulas. This is exactly the kind of shared quadrature/grid-spacing logic the checklist asks about, and consolidating into one shared helper (checking both `s` and `ds`, used by both files) would both remove the duplication and close the §5 correctness gap in one move.
- **New, within `wavefunctions.jl`**: the de Broglie grid-sizing formula `max(round(Int, k*d*b/(2*pi)), 512)` is copy-pasted **three times** — once for `boundary_limits`'s `grd` argument and once each for `nx`/`ny` in `wavefunction(state::S)`, `wavefunction(state::BIMEigenstate)`, and `wavefunction(state::BasisState)` (6 near-identical inline expressions total across the file). A small private helper (e.g. `_debroglie_grid_size(k, d, b) = max(round(Int, k*d*b/(2*pi)), 512)`) would remove the repetition with zero behavior change.
- **Minor**: `wavefunction(state::BIMEigenstate; use_chebyshev=true)` computes its own ad hoc radial padding (`rmax = 1.05*sqrt(dx^2+dy^2)`) inline rather than reusing the shared `_cheb_geom_rminmax` padding helper from `solvers/chebyshev/optimalpanelization.jl` (qb-06 scope). The two aren't literal duplicates (one pads a grid-to-boundary bounding-box diagonal, the other pads boundary-to-boundary pairwise extrema), but both implement the same "pad the observed geometric extent before building Chebyshev panels" idea independently — worth a one-line note for whoever next touches either.
- `compute_psi`'s memory-exceeded fallback branch uses `println("Warning: ...")` ([wavefunctions.jl#L217](../../../../.julia/dev/QuantumBilliards.jl/src/states/wavefunctions.jl#L217)) instead of `@warn`, inconsistent with idiomatic Julia logging used elsewhere in the package (`@debug`/`@timeit_debug` conventions per `julia-solver-debug-timing`) — a raw `println` can't be filtered/suppressed like a proper log level. Minor style fix.

## 8. Threading
- **Compliant**: `wavefunction(state::BIMEigenstate)`'s grid-evaluation loop ([wavefunctions.jl#L370-L375](../../../../.julia/dev/QuantumBilliards.jl/src/states/wavefunctions.jl#L370-L375)) uses `@use_threads multithreading=multithreaded for jj in eachindex(idxs)`, writes to disjoint indices of a preallocated `Psi`, no `push!` — matches the mode's threading convention exactly.
- **Weakness (minor)**: `compute_psi`'s memory-limit-exceeded fallback path ([wavefunctions.jl#L219-L231](../../../../.julia/dev/QuantumBilliards.jl/src/states/wavefunctions.jl#L219-L231)) — precisely the code path taken for *large* basis dimensions where performance matters most — loops over basis coefficients sequentially with no `@use_threads` wrapping, unlike the main-path `basis_matrix(...; multithreaded)` call just above it which does thread internally. Since each iteration's `basis_fun(basis,i,k,pts)` call already vectorizes over all points, threading here would parallelize over basis functions (independent accumulation into `Psi`, would need a reduction or per-thread partial-sum pattern rather than a naive disjoint-write loop) — flagging as a missed-threading candidate, not a correctness bug.
- **Documented, deliberate non-issue**: the Husimi general-quadrature core (husimifunctions.jl) and the fast stencil are both single-threaded, per migration-plan 05.6's own explicit rationale ("normally called once per already-computed state ... not in a hot per-state batch loop"). No violation given typical grid sizes (~(100,50)); noting only for completeness since the checklist explicitly asked about per-point Husimi loops.
