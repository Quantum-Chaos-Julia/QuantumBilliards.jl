### Unstable APIs
- [decompositions.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/decompositions.jl#L32-L57) `generalized_eigen`/`generalized_eigvals`: `q=1.0./sqrt.(d[idx])` uses a hardcoded `Float64` literal `1.0` instead of `one(eltype(d))`. For a `Float32` `A`/`B` (a legitimate call pattern given `AbsBasisSolver`'s generic `eltype(B)`-driven matrix construction), this silently promotes `q` to `Float64`, forcing `scale_cols!` to compute a `Float64` intermediate per column before truncating back into the `Float32` `C_scaled` — an avoidable type instability/extra allocation, not just a style nit.
- Item 4's specific question — **do `generalized_eigen`/`generalized_eigvals`/`generalized_eigen_all` return the same eigenvalue/eigenvector element-type family for the same input type?** No: for identical real `A,B`, `generalized_eigen`/`generalized_eigvals` (symmetric truncated-basis method) return **real** `mu`, while `generalized_eigen_all` (general QZ via `eigen(A,B)`) always returns **complex** `λ`/`VR`/`VL`, by design (documented, and required because EBIM's `B` pencil is singular/ill-conditioned). The shared "generalized eigen*" naming across genuinely different algorithms/return-type families is a real but low-severity documentation/naming footgun — not a bug, since call sites (`decompositionmethod.jl#L300`, `verginisaraceno.jl#L344`) correctly combine `C*Z` per the (accurate) docstrings, and EBIM/Beyn callers correctly expect complex output.
- [decompositions.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/decompositions.jl#L195-L209) `adjust_scaling_and_samplers`: `bs = solver.pts_scaling_factor` / `samplers = solver.sampler` are aliases, not copies — `push!` inside the function **mutates the solver's own stored fields as a side effect** of what its name/docstring present as a pure query returning "the adjusted vector." Confirmed **not currently a race**: every call site (`decompositionmethod.jl`, `particularsolutions.jl`, `verginisaraceno.jl`'s `evaluate_points`) is only ever reached from a serial `while`-loop `compute_spectrum(::AcceleratedBasisSolver,...)` — unlike `BeynSolver`'s per-window `evaluate_points`, no basis-solver `compute_spectrum` path threads across windows on a shared solver instance today. Still worth a docstring note (or switching to `copy`) since it's a latent footgun if a future basis-solver windowed-threading path is added mirroring Beyn's.
- `BoundaryPoints`/`BoundaryGeomCache`/`BoundaryPanelArrays` field concreteness: ✓ all fields concretely typed (`Vector{T}`, `Vector{SVector{2,T}}`, `Int`, `Bool`), no `Any`/abstract fields.

### Vulnerabilities
- [matrixconstructors.jl](../../../.julia/dev/QuantumBilliards.jl/src/solvers/matrixconstructors.jl#L123-L169): `_scale_rows!`/`_scale_rows_sqrtw!`/`_build_Bn_inplace!` all use `@inbounds` while indexing a second array (`w`/`normals`) by the *first* array's row index, with no length check anywhere in the function bodies. The invariant is currently upheld only because their sole live call sites always pass `pts.ds`/`pts.w_dm`/`pts.normal` straight from a `BoundaryPoints` object, whose *inner constructor* validates matching lengths — but that guarantee lives in a different file and isn't re-asserted here. If any future caller passes a plain `Vector` not sourced from a validated `BoundaryPoints`, a length mismatch becomes silent memory corruption (out-of-bounds `@inbounds` read/write), not a clean `BoundsError`. Low severity today, but worth at least a one-line comment on each function documenting the length-matching precondition it relies on.
- `solve_state` ([sweepmethods.jl#L309](../../../.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/sweepmethods.jl#L309)) is a **new, previously-unaudited call site** of `@blas_1` (`@blas_1 vals, lvecs, rvecs, _ = KrylovKit.svdsolve(A, 1, :SR)`), joining the `@blas_1`/`@blas_multi_then_1` race condition already flagged in the qb-01 findings (global, non-restored `BLAS.set_num_threads` state, no `try/finally`). Since `solve_state` is the one path every `SweepBIMSolver`'s `compute_eigenstate` now goes through, this widens (rather than narrows) the surface of that pre-existing race/exception-safety gap — flagging for awareness, not re-analyzing the root cause here (already qb-01's finding).
- `generalized_eigen`/`generalized_eigvals` ([decompositions.jl#L32-L109](../../../.julia/dev/QuantumBilliards.jl/src/solvers/decompositions.jl#L32-L109)): if every eigenvalue of `A` fails the `d .> eps*maximum(d)` cutoff (fully rank-deficient `A`), `idx` is all-`false`, `C`/`C_scaled` become `0`-column matrices, and the function returns an **empty** `mu`/`Z` silently instead of raising an error — a genuinely ill-conditioned/degenerate matrix pencil is not surfaced to the caller, matching the checklist's "silent fallback on ill-conditioning" concern. `generalized_eigen_all` does the opposite (filters `NaN`/`Inf` explicitly, per its own well-reasoned docstring) but has the same latent gap: if literally every generalized eigenvalue comes back `NaN`/`Inf` (a genuinely singular pencil, which the docstring itself says is expected near non-eigenvalue `k`), it silently returns empty `λ`/`VR`/`VL` rather than erroring — callers must know to check `isempty(λ)` themselves.
- `boundarygeomcache.jl`'s `kappa` field was verified to still use the diagonal-kernel-limit normalization (`κ = (1/2π)·(-(x'y''-y'x''))/(x'²+y'²)`, i.e. **speed² denominator**, not the Frenet speed³), distinct from and not consolidated with `BilliardGeometry.jl`'s new generic `curvature()` — Gap 4 from the geometry audit remains correctly respected, no accidental merge found.
