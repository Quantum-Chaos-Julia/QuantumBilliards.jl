## Ground-truth correction to the pre-existing memory note

The repo memory note dated 2026-09-10 claims: *"main's `solvers/chebyshev/bessels.jl`'s
scalar `eval_h`/`eval_j` ... are MISSING the intermediate `|k*r| <
hankel_z_chebyshev_cutoff (0.2)` branch that -develop's chebyshev_bessels.jl
applies everywhere ... a genuine accuracy-fidelity regression."*

This audit traced the actual hot-loop call path in both repos and found the
claim is **incorrect as stated**:

* `-develop`'s own scalar `eval_h`/`eval_j` (`chebyshev_bessels.jl:717,753`)
  only check `pidx==0` — no intermediate cutoff at all (worse than claimed,
  not better).
* Main's scalar `eval_h` (`bessels.jl:219`) **does** include the
  `pidx==0 || abs(z)<hankel_z_chebyshev_cutoff` guard.
* Neither repo's DLP/CFIE derivative-kernel hot loop
  (`_dlp_kernel_entry_with_derivatives_cheb` in main /
  `_one_k_nosymm_DLP_chebyshev_derivatives!` → `h0_h1_multi_ks_at_r!` in
  `-develop`) is missing the guard: `-develop`'s multi-k evaluator
  `h0_h1_multi_ks_at_r!` has it, and main's scalar `eval_h` has it too.
* For the **value-only** path, main is actually strictly *more* conservative
  than `-develop` (main's `eval_h` has the guard; `-develop`'s
  `eval_h_multi_ks!` used by the value-only assembly does not).

**No action item results from this specific claim.** It is superseded by the
real findings below. Update the repo memory note accordingly once this file
is read (see "Memory update" at the end).

## Findings, in priority order

### 1. [Accuracy risk] No radial-interval padding margin before building Chebyshev plans

* `-develop`: `build_dlp_kress_block_cache`/`build_cfie_kress_block_caches`
  (`chebyshev_dlp_kress.jl:147`, `chebyshev_cfie_kress.jl:219`) default to
  `pad::Tuple{T,T}=(0.95,1.05)`, widening every observed
  `rmin`/`rmax` by ±5% before building panels: `rrmin=pad[1]*rmin0`,
  `rrmax=pad[2]*rmax0`.
* Main: [`_cheb_geom_rminmax`](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/chebyshev/optimalpanelization.jl#L26-L46)
  uses the raw observed pairwise-distance extrema from `G.R` with **no
  margin**. Because `_find_panel_uniform`/`panel_and_geom` silently **clamp**
  any out-of-range `r` to the first/last panel (no error, no warning), a
  radius slightly above the sampled `rmax` — plausible whenever a later call
  in the same accelerated solve (e.g. `ExpandedBIMSolver`'s `k_corr` residual
  check, or a different Beyn window reusing the same boundary) evaluates a
  pairwise distance not present in the exact sample used to build the plan —
  gets silently extrapolated with unbounded interpolation error.
* **Fix**: add a `pad::Tuple{Float64,Float64}=(0.95,1.05)` margin to
  `_cheb_geom_rminmax` in
  [optimalpanelization.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/chebyshev/optimalpanelization.jl),
  matching `-develop`'s default, applied as `rmin *= pad[1]; rmax *= pad[2]`
  before the `rmin_cheb` floor/`rmin<rmax` validation. Thread it through
  `tune_dlp_cheb_plans`/`tune_cfie_cheb_plans` call sites in
  [beyn.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/acceleratedmethods/beyn.jl)
  and
  [ebim.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/acceleratedmethods/ebim.jl)
  unchanged (no new keyword needed at the solver level — this is an internal
  safety margin, not a user-tunable knob, exactly as in `-develop`).

### 2. [Performance] Beyn's multi-k assembly does `nq` separate O(N²) passes instead of one combined pass

* `-develop`: `_all_k_nosymm_DLP_chebyshev!`/`_all_k_nosymm_DLP_chebyshev_derivatives!`
  (`chebyshev_dlp.jl:411-527`) loop over boundary pairs `(i,j)` **once**,
  computing geometry (`dx,dy,r,invr`, panel/coordinate lookup) once per pair,
  then evaluate **all `Mk` wavenumbers inside that single innermost loop**
  via `h0_h1_multi_ks_at_r!`/`h1_j1_multi_ks_at_r!`, using per-thread reusable
  buffers (`DLPDerivChebWorkspace`, `chebyshev_dlp.jl:313-343`) before
  scattering into `Ks[m][i,j]` for every `m`.
* Main: [`_construct_matrices_multi_k_cheb`](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/acceleratedmethods/beyn.jl#L208-L259)
  instead calls `_dlp_fredholm_full_cheb!`/`_cfie_fredholm_full_cheb!` (and
  the `_reduced_cheb!` symmetry variants) **once per contour node `m`**,
  each pass re-streaming the full `G.R`/`G.invR`/`G.logterm`/`G.inner` arrays
  and recomputing `panel_t` for every `(i,j)` pair from scratch. This is
  `nq` (default 48) full re-reads of the O(N²) geometry cache instead of one
  — a genuine, measurable extra memory-bandwidth cost for large boundary
  discretizations. The combinator functions needed to fix this
  (`h0_h1_multi_ks_at_r!`, `h1_j1_multi_ks_at_r!`,
  `h0_h1_j0_j1_multi_ks_at_r!`) are **already ported verbatim** in
  [bessels.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/chebyshev/bessels.jl)
  but currently unused — this is a wiring gap, not a missing-primitive gap.
* **Fix**: port `-develop`'s single-pass, all-`k`-per-pair assembly pattern
  as new functions in
  [dlp.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/chebyshev/dlp.jl)/
  [cfie.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/chebyshev/cfie.jl)
  (e.g. `_dlp_fredholm_full_multi_k_cheb!(Tbufs, pts, Rmat, G, zj, plans1,
  plansj1; multithreaded)` writing directly into `Tbufs[m][i,j]` for every
  `m` inside the single `(i,j)` loop, mirroring `-develop`'s
  `DLPDerivChebWorkspace` per-thread buffer reuse), plus symmetry-reduced
  variants matching the existing `_dlp_fredholm_reduced_cheb!` shape. Update
  `_construct_matrices_multi_k_cheb` in
  [beyn.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/acceleratedmethods/beyn.jl)
  to call the new single-pass function instead of looping `for m in
  eachindex(zj)` over the per-node assembly. `ExpandedBIMSolver`/`ebim.jl` is
  **not** affected — it evaluates one `k` (plus derivatives) at a time via
  `_dlp_kernel_entry_with_derivatives_cheb`, not a batch of contour nodes, so
  this specific regression is Beyn-only.

### 3. [Minor performance] No k-independent panel-index cache reused across a sweep

* `-develop`: `DLPKressBlockCache`/`CFIEKressBlockCache` precompute
  `pidx`/`tloc` matrices once per fixed boundary discretization (they depend
  only on geometry, not `k`), reusable across an entire wavenumber sweep.
* Main: `panel_t(plan, r)` is recomputed on every `construct_matrices` call
  (every Beyn window, every EBIM correction step). The arithmetic itself is
  O(1) per pair, so this is minor compared to finding 2, and compounds with
  it rather than standing alone.
* **Fix (optional, lower priority)**: once finding 2's single-pass rewrite
  lands, consider whether `panel_and_geom`/`panel_t` results for a fixed
  boundary discretization could be cached and passed into the new multi-k
  assembly function across `compute_spectrum`'s Weyl-window loop
  ([spectra/spectralutils.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/spectra/spectralutils.jl)).
  Do not implement this ahead of finding 2 — it only pays off once the
  single-pass assembly exists to receive a shared cache.

### 5. [Negligible, style-only] Redundant `z`/cutoff computation in derivative kernel entries

* Main's `_dlp_kernel_entry_with_derivatives_cheb`
  ([dlp.jl:102-114](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/chebyshev/dlp.jl#L102-L114))

  singleton plan list) computes `z`/the cutoff decision once for both H0 and
  H1. Same pattern in `cfie.jl`'s derivative entry.
* **Fix (lowest priority, do last if time allows)**: add a scalar
  `eval_h0_h1_pair(plan0, plan1, pidx, t, r)` helper in

  it from `_dlp_kernel_entry_with_derivatives_cheb`/
  `_cfie_kernel_entry_with_derivatives_cheb`. Purely an inner-loop micro
  -optimization; skip if it complicates the diff for no measurable gain
  (benchmark before committing to this one).
