# Step 9.5 — `compute_spectrum` for accelerated BIM solvers

Status: **Implemented.** This step's code has already landed in
`QuantumBilliards.jl` (not just planned) — this file documents what was done
and why, for the same reasons every other step file exists: a durable
reference for the next step (10) and for the Julia Test Writer subagent.

## Goal

Steps 8/9 gave `BeynSolver`/`ExpandedBIMSolver` a *single-window*
`solve_spectrum` (one Beyn contour, or EBIM local corrections applied to a
caller-supplied batch of trial `k`s) but nothing that covers a *whole*
wavenumber range `[k1,k2]` the way `compute_spectrum(::AbsBasisSolver, ...)`
already does for basis solvers. `-develop` has exactly this at a wider scope
— `solve_spectrum_beyn`/`solve_spectrum_ebim` — each with a genuinely
different merge strategy suited to its own solver's failure modes. Port both
as new `compute_spectrum` methods dispatched on the concrete accelerated-BIM
solver type (not a `method::Symbol` dispatch the way `-develop` does it,
since main already distinguishes `BeynSolver`/`ExpandedBIMSolver` as
distinct structs — see the top-level plan §2 architecture decisions).
Also introduce `ChebyshevConfig`, so Step 10 has a single configuration
object to build against instead of continuing to scatter
`n_panels_h`/`M_h`/`n_panels_j`/`M_j` across struct fields and, eventually,
dozens of auto-tuning keyword arguments the way `-develop` does.

## Preconditions

Steps 8 and 9 complete (`BeynSolver`/`ExpandedBIMSolver`'s single-window
`solve`/`solve_spectrum` already implemented and passing their existing
`test/solvertests.jl` cases with `use_chebyshev=false`).

## Implementation notes

### `SpectralData` extension

Added one new field, `ten2::Union{Nothing,Vector{T}}` (default `nothing` via
a keyword argument on the existing 3-positional-argument constructor), for a
*secondary* tension/residual measure — e.g. a future `BeynSolver` path that
reports both a raw and a normalized nonlinear residual (`-develop`'s
`tens`/`tensN`). Neither new `compute_spectrum` method populates it yet
(both report a single tension), but the field exists so a solver that
*does* need a second quality measure doesn't require another struct.
`merge_spectra`/the generic `AbsBasisSolver` `compute_spectrum` are
unaffected (every existing 3-arg `SpectralData(k,ten,control)` call site
still works unchanged, `ten2` defaults to `nothing`).

### `compute_spectrum(solver::BeynSolver, billiard, k1, k2; ...)`

Reuses **all** already-implemented, already-tested Step 8 machinery —
`plan_weyl_windows`, `beyn_disks_from_windows`, `evaluate_points`, `solve` —
unchanged. Per-window boundary-point evaluation is independent and safe to
multithread across windows (`multithreaded_windows`, default `true`); the
per-window `solve` call is left in a plain sequential loop (the per-contour-
node loop inside `construct_matrices(::BeynSolver,...)` is deliberately
single-threaded already, see Step 8's own note, so parallelizing at this
outer level too would not conflict but was intentionally kept sequential to
match `-develop`'s own `solve_spectrum_beyn`, which does not thread its main
per-disk pass either — only its initial point-evaluation pass). Since
`plan_weyl_windows` tiles `[k1,k2]` into contiguous, non-overlapping windows
by construction, results are plainly concatenated and sorted — no
`overlap_and_merge!`/`overlap_and_merge_ebim!` call, matching `-develop`
exactly (which does not deduplicate across window boundaries either).
`solver.m`/`nq`/`r`/`svd_tol`/`res_tol`/`auto_discard_spurious` are read
directly from `solver` (not re-exposed as `compute_spectrum` keyword
arguments), since main's `BeynSolver` already stores them as fields — unlike
`-develop`'s `solve_spectrum_beyn`, whose `BeynSolver` is a mere `Union`
trait with no fields of its own.

### `compute_spectrum(solver::ExpandedBIMSolver, billiard, k1, k2; ...)`

Ported `-develop`'s adaptive `k += dk(k)` trial-grid construction and
`seg_reuse_frac`-gated boundary-discretization reuse verbatim (only the
`pts`-reuse condition was rewritten from `-develop`'s
`seg_last==1 ? pts0 : evaluate_points(...)` — which only ever reuses the very
first `evaluate_points` call for a single-point first segment and otherwise
silently discards it — to a general `seg_last==seg_first` check that reuses
`pts` correctly for *every* segment, not only a trivial first one; this is a
control-flow correction, not a numerical-kernel change, so it does not
violate the fidelity rule). Each trial `k` is corrected independently via the
already-implemented Step 9 `solve(solver::ExpandedBIMSolver, pts, k)`; ported
`overlap_and_merge_ebim!` (+ `_local_gap`/`_ebim_scoring_logic`) verbatim into
`spectralutils.jl`, with one adaptation: `-develop`'s `_local_gap` uses
`Statistics.median`; reimplemented the (tiny, `2*local_window+1`-element)
median by hand instead of adding `Statistics` as a new package dependency,
per the "avoid introducing external dependencies unless clearly justified"
guidance — this is a pure control-flow/utility substitution, not a change to
any numerically sensitive kernel.

`-develop`'s per-`k` matrix-buffer reuse (`allocate_ebim_matrices`+`solve!`,
reusing preallocated `A`/`dA`/`ddA` across an entire segment) was **not**
ported, because main's Step 9 `ExpandedBIMSolver` never got a mutating
`solve!`/`allocate_ebim_matrices` counterpart to begin with — only the
non-mutating `solve(solver, pts, k)`, which allocates fresh matrices every
call via `construct_matrices`. Porting the buffer-reuse optimization would
mean adding a new mutating API surface to `ExpandedBIMSolver` that Step 9
never introduced, which is out of scope for a `compute_spectrum`-wiring step;
flagged here explicitly so a future performance pass can add it without
re-discovering the gap. The `pts`-reuse (avoiding repeated boundary
quadrature/Kress-correction/symmetry-orbit setup across nearby trial `k`s)
was still ported, since it needs no new solver API.

### `ChebyshevConfig`

A single struct (`n_panels_h`, `M_h`, `n_panels_j`, `M_j`, `tol`, `max_iter`,
`sampling_points`, `grow_panels`, `grow_M`, `param_strategy`) replacing the
four individual fields previously on `BeynSolver`/`ExpandedBIMSolver`.
Confirmed via `grep` before refactoring that `n_panels_h`/`M_h`/`n_panels_j`/
`M_j` were referenced nowhere outside each solver's own struct
definition/constructor/docstrings (Chebyshev evaluation itself is still
unimplemented, guarded by the existing `solver.use_chebyshev && error(...)`
checks), so this was a safe, self-contained rename/consolidation. Both
constructors keep accepting the same four keyword arguments for backward
compatibility (building a default `ChebyshevConfig` internally), plus a new
`cheb_config::Union{Nothing,ChebyshevConfig}=nothing` keyword to pass a
pre-built configuration (e.g. one already auto-tuned and reused across many
`compute_spectrum` calls, once Step 10 implements auto-tuning).

## Performance & fidelity notes

* Every numerically sensitive piece reused here (`plan_weyl_windows`,
  `beyn_disks_from_windows`, `_beyn_solve_core`'s contour/residual pipeline,
  the EBIM `_ebim_lin1_deriv`/`_ebim_const0_deriv` kernels) is **Step 8/9
  code, untouched** — this step only adds the wavenumber-range driver and
  merge logic around them, per the "reuse existing utilities" guidance.
* `overlap_and_merge_ebim!`'s clustering logic (adaptive tolerance from the
  local median gap, the `log10(|Im k|+eps)+log10(|tension|+eps)` scoring) was
  ported arithmetic-for-arithmetic from `-develop`, since it is exactly the
  kind of low-level numeric decision logic the fidelity rule protects.
* Manually verified end-to-end against the Veech triangle (`BeynSolver` +
  `DoubleLayerPotentialSolver`/`GlobalCornerGrading`) and the symmetric
  circle (`BeynSolver`/`ExpandedBIMSolver` + `CombinedFieldIntegralEquationSolver`/
  `SmoothPeriodicGrading`/`YAxisReflection`) fixtures already used by
  `test/solvertests.jl`; `compute_spectrum(::BeynSolver, ...)` reproduces the
  same eigenvalues as the existing single-window tests over a wider range
  with no duplicates. `compute_spectrum(::ExpandedBIMSolver, ...)` was
  observed to produce a "trail" of only partially-converged local
  corrections away from a true root, collapsing into a single tight,
  low-tension cluster only near the root itself — this reflects the
  *already-merged Step 9* second-order local correction's limited radius of
  convergence for a one-step Taylor expansion (not a bug introduced here);
  the merge tolerances (`tol`/`spacing_frac`/`tolmax`/`local_window`) are
  exposed precisely so a user can tune them (or supply a finer `dk`) per
  problem, matching `-develop`'s own tunable design.
* `DoubleLayerPotentialSolver` (pure DLP, no `ikS(k)` term) wrapped in
  `ExpandedBIMSolver` on the Veech triangle with `GlobalCornerGrading`
  returned `NaN` from `solve` for every trial `k` tested, including `k`
  essentially equal to a Beyn-verified true eigenvalue. This is a
  **pre-existing Step 9 numerical issue** (likely `A'(k)` being singular or
  near-singular for the plain-DLP kernel, or the `eigen(A,dA)`/`eigen(A',dA')`
  primal/adjoint eigenvector pairing failing to match up), reproducible with
  or without this step's `compute_spectrum` wrapper (confirmed by calling
  `solve(solver::ExpandedBIMSolver, pts, k)` directly). Out of scope for this
  wiring-only step; flagged here for whoever next audits `ExpandedBIMSolver`
  numerics (Step 10's Chebyshev pass touches the same kernel-derivative code
  and should re-check this).
