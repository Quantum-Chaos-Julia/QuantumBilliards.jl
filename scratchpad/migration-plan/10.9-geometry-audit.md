# Step 10.9 — `BilliardGeometry.jl` vs `BilliardGeometry-develop` geometry/symmetry audit

Status: **Read-only structural audit and migration/improvement plan. No source
code was changed by this step.** Ordered after Step 10.5 and before Step 11
per the user's explicit request: land any symmetry/geometry consolidation
*before* Step 11 starts porting new billiards, so the new billiards are
written against the final API, not against something that gets reshuffled
immediately afterward.

## Goal

Audit every geometry/symmetry file shared between `BilliardGeometry.jl` and
`BilliardGeometry-develop` (excluding the billiard catalogue itself, which is
Step 11's job) to answer four questions the user asked directly:

1. Is anything from `-develop` genuinely missing (not yet ported), beyond the
   already-known billiard files?
2. Can the symmetry framework be streamlined/made more extensible (easy to add
   a new symmetry type and have it dispatch correctly everywhere) without a
   redesign?
3. Should `PolarSegment` (current, Fourier-coefficient-only) be renamed to
   `FourierCoeffPolarSegment`, with a new, more general function-based
   `PolarSegment` taking its place — and what does that rename touch?
4. How does all of this interact with the boundary-condition (`AbsBoundaryCondition`)
   structs, and can billiard constructors be simplified?

### Real gaps found (these need a plan, not just a docstring pass)

#### Gap 1 — Antisymmetric BIM sectors are silently unreachable for the three most common reflection symmetries

[BilliardGeometry.jl/src/geometry/symmetryorbits.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/symmetryorbits.jl)'s
`symmetry_index_orbits` methods for `XAxisReflection`, `YAxisReflection`,
`XYAxisReflection` and `NFoldRotation` all call `_build_symmetry_orbit_map`
**without** passing irrep-character scales, so they default to
`ones(Complex{T}, ng)` — the trivial representation only. Meanwhile
`DiagonalReflection`/`AntiDiagonalReflection` *do* pass
`symmetry_irrep_character(T, symmetry)`. This is inconsistent, and the
existing docstring even says so explicitly ("Only the trivial representation
is supported... odd/anti-symmetric BIM sectors are not yet implemented").

Compared against `QuantumBilliards-develop/src/states/symmetry/symmetry_orbits.jl`
(lines ~320–398): `-develop` *does* pass `symmetry_irrep_character` for
`XAxisReflection`/`YAxisReflection`/`XYAxisReflection` (e.g.
`_build_periodic_symmetry_orbit_map(T,[id,refl],[one(Complex{T}),χ])`), and its
`NFoldRotation` path (`_rotation_orbits`) uses the rotation's `sector`/character
too. `symmetry_irrep_character` already exists for every one of these types in
main's `symmetry.jl` (confirmed above) — **the fix is purely wiring the
already-existing function into the already-existing dispatch methods**, not a
new abstraction.

Impact: every `SweepBIMSolver` with `solver.symmetry` set to any of these four
types can currently only ever fold the fully-symmetric sector. Any billiard
with a genuine antisymmetric eigenstate below the sector's own fully-symmetric
ground state would be silently missed by `compute_spectrum`/`k_sweep` — a
correctness gap, not just a missing feature.

#### Gap 2 — No multicomponent (multiply-connected) symmetry-orbit folding

`-develop`'s `symmetry_orbits.jl` has an entire "MULTICOMPONENT EXACT ORBITS"
section (overloads of `symmetry_index_orbits` taking `pts::Vector{BoundaryPoints{T}}`,
one physical ring per component — outer boundary + each hole — since a
symmetry acts *within* each ring, or maps one ring to another, but the
single-ring `mod1`-based index-permutation formulas
(`_idx_reflect_x`/`_idx_reflect_y`/`_idx_rotate`, etc.) are only valid for one
contiguous periodic ring of length `N`).

Main's `symmetry_index_orbits` only has the single-flat-`xy` overload. Yet
[solvers/sweepmethods/compositebim.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/sweepmethods/compositebim.jl)
(line ~391/438) calls `symmetry_index_orbits(T, pts.xy, solver.symmetry)` on
the **flattened concatenation of every component's points** whenever
`solver.symmetry !== nothing`. For a simply-connected symmetric billiard this
is fine (one ring), but for a genuinely multiply-connected symmetric billiard
(a symmetric `sinai`/`circle_with_hole` from Step 11) the single-ring `mod1`
arithmetic will index across ring boundaries incorrectly whenever the outer
ring and a hole have different node counts, or a symmetry maps one hole to a
different hole. This directly explains *why* Step 7's deferred
`CompositeBIMSolver` verification note ("full numerical verification ...
once a real multiply-connected billiard exists") is deferred: the missing
piece isn't only a test fixture, it's a **missing code path**
(`symmetry_index_orbits` needs a `Vector{BoundaryPoints}`/per-component
overload before a symmetric multiply-connected billiard can be solved
correctly at all).

#### Gap 3 — `full_boundary` has no method for polar-parametrized curves

[BilliardGeometry.jl/src/geometry/fullboundary.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/fullboundary.jl)'s
`_apply_symmetry_to_curve`/`_reverse_curve` dispatch only has methods for
`LineSegment` and `CircleSegment` — there is no method for `AbsPolarCurve`
(neither the renamed-to-be `FourierCoeffPolarSegment` nor the new
function-based `PolarSegment`). Step 11's rotationally/reflection-symmetric
polar billiards (`star.jl`, `c3.jl`, and any future symmetric `circle.jl`
variant) will hit a `MethodError` the moment `full_boundary(billiard)` is
called on them with a non-empty `symmetries` field, unless this gets added.

Confirmed via `-develop`'s actual `StarBilliard`/`C3Billiard` sources
(`BilliardGeometry-develop/src/geometry/billiards/star.jl`, `c3.jl`) that
these billiards hand-maintain their own `full_boundary::Vector{AbsCurve}`
field (one whole-circle `FourierCoeffPolarSegment`, not reconstructed by
rotating the fundamental sector) — exactly the pattern Step 4 already
replaced for `LineSegment`/`CircleSegment` billiards. Porting these two
billiards in Step 11 using main's `full_boundary(billiard)` design (per Step
4's stated goal of *not* hand-maintaining a `full_boundary` field per
billiard) requires this new dispatch method to exist first.

Design (same shape as the existing `CircleSegment` method): for a polar curve
centered at `c` with `shift_angle`/`arc_angle`, under a symmetry with 2x2
linear map `M = _sym_matrix(sym)`:
* `NFoldRotation`/other rotations (`det M = +1`): new center `c' = M*c`, new
  `shift_angle' = shift_angle + φ` where `φ = atan(M[2,1], M[1,1])`, radial
  function unchanged (rotating a polar curve about a possibly-off-origin
  center rotates its local origin too, not just its angular phase — the
  `FourierCoeffPolarSegment`/`PolarSegment`'s own `R`/`coef`/`r_func` are
  invariant under rotation of the ambient frame).
* Reflections (`det M = -1`): reflecting a polar curve reverses angular
  direction; same `_reverse_curve` treatment as `CircleSegment` applies
  (negate `arc_angle`, then `_reverse_curve` restores a positive one) — valid
  whenever the reflected billiard is a symmetry of the *same* `r_func`/`coef`
  (true for every symmetric polar billiard by construction, since the
  symmetry group is only ever declared when the radial function actually has
  that symmetry).
* `_reverse_curve` for `AbsPolarCurve`: `new_shift = shift_angle + arc_angle;
  new_arc = -arc_angle` (identical formula to `CircleSegment`'s, since it only
  depends on the angular parametrization convention, not on the radial
  function type).

#### Gap 4 — Missing generic curve-derivative utilities (`tangent_vec`, `normal_vec`, `curvature`)

Main already has [BilliardGeometry.jl/src/geometry/curvederivatives.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/curvederivatives.jl)
(91 lines: `tangent`/`tangent_2` generic array fallback + `LineSegment`,
`CircleSegment`, Fourier-coefficient `PolarSegment` analytic derivatives —
this already matches the bulk of `-develop`'s
`segments/curve_derivatives.jl`, 404 lines). What main is missing, confirmed
by a workspace-wide search turning up **zero** hits in either
`BilliardGeometry.jl` or `QuantumBilliards.jl`:

* `tangent_vec(crv, ts)` — unit tangent, `v(t)/norm(v(t))`.
* `normal_vec(crv, ts)` — unit outward normal via the 90°-rotation convention
  `(tx,ty) -> (ty,-tx)` (documented as correct for a CCW outer boundary; holes
  need the opposite orientation for the same rule to give the outward normal).
* `curvature(crv, ts)` / `curvature(crv, t)` — signed curvature
  `(x'y''-y'x'')/(x'^2+y'^2)^{3/2}`, reusing `tangent`/`tangent_2` generically
  for any `<:AbsCurve`.
* `tangent`/`tangent_2` for the (not-yet-ported) function-based `PolarSegment`,
  via nested `ForwardDiff.derivative` calls on `curve(polar_curve, t)`
  (`ForwardDiff` is already a direct dependency of `BilliardGeometry.jl` —
  confirmed in `Project.toml`, so this needs no new dependency).

These are genuinely reusable, generic geometry utilities (not solver-specific)
that belong in `curvederivatives.jl` per the file's existing scope. Note:
[QuantumBilliards.jl/src/solvers/boundarygeomcache.jl](/home/clozej/.julia/dev/QuantumBilliards.jl/src/solvers/boundarygeomcache.jl)'s
`boundary_geom_cache` independently computes a **differently-normalized**
scaled curvature (`kappa = -(dX·ddY-dY·ddX)/(2π·(dX²+dY²))`, i.e. divided by
speed², used directly as the DLP/CFIE diagonal-kernel limit) straight from raw
`tangent`/`tangent_2` arrays — this is deliberately not the same quantity as
the geometric `curvature()` above (which divides by speed³) and must **not**
be replaced by a call to it; the two coexist for different purposes. No
change needed there.

#### Gap 5 — `PolarSegment`/`FourierCoeffPolarSegment` rename impact

Confirmed: main's current `PolarSegment{T,BC,N}` in
[segments/polarcurves.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/polarcurves.jl)
is content-identical (Fourier-coefficient radial function, same field layout)
to `-develop`'s `FourierCoeffPolarSegment{T,BC,N}` in `segments/polarsegment.jl`,
modulo two real (not just cosmetic) differences worth fixing during the
rename, not just carrying over:
1. Main's constructor does **not** promote `R`/`arc_angle`/`shift_angle`/`center`
   to a common type with `coef` — it uses `type = eltype(coef)` alone and
   stores the raw literals, which can silently construct a struct whose `T`
   parameter doesn't match e.g. an `Int` `R=1` or a `Float32` `center`.
   `-develop`'s `T = promote_type(eltype(coef), typeof(R), typeof(arc_angle),
   typeof(shift_angle), eltype(center))` is the correct, type-stable pattern
   and should be adopted under the new `FourierCoeffPolarSegment` name.
2. `-develop` additionally has a **new, distinct, more general**
   `PolarSegment{T,BC,F}` (arbitrary `r_func::F(φ)`, e.g. an
   interpolation/spline or any closure, not restricted to a Fourier series),
   with `tangent`/`tangent_2` implemented via `ForwardDiff` (Gap 4) instead of
   an analytic formula. This is what should become the *new* `PolarSegment`.

Rename call-site impact (every one confirmed by direct search, this is the
complete list — no other call sites exist in the workspace):
* [BilliardGeometry.jl/src/geometry/segments/polarcurves.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/segments/polarcurves.jl) — the struct/constructor/`polar_radius` itself.
* [BilliardGeometry.jl/src/geometry/curvederivatives.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/curvederivatives.jl) — `_polar_radius_derivative`/`_polar_radius_derivative_2`/`tangent`/`tangent_2` all dispatch on `L<:PolarSegment`.
* [BilliardGeometry.jl/src/geometry/billiards/polar.jl](/home/clozej/.julia/dev/BilliardGeometry.jl/src/geometry/billiards/polar.jl) — `PolarBilliard(coef; ...)` calls `PolarSegment(coef; center=center)` (Fourier-coefficient convention) — this is the **only** existing billiard call site in the whole workspace and must switch to `FourierCoeffPolarSegment(coef; center=center)`.
* Step 11's not-yet-written `circle.jl`/`ellipse.jl`/`star.jl`/`c3.jl`/`prosen.jl` must be written directly against the *new* naming (`-develop`'s own `star.jl`/`c3.jl` sources already call `FourierCoeffPolarSegment`, confirming this is exactly the target API) — this is precisely why the user wants this rename to land before Step 11 starts.
* No usages found in `QuantumBilliards.jl`, `QBPlotting.jl`, or any test file — the rename's blast radius is fully contained inside `BilliardGeometry.jl` plus Step 11's not-yet-written code.

Also worth a minor, bundled fix while touching `polar.jl`:
`PolarBilliard`'s `symmetries = []` is an untyped `Vector{Any}` literal (works
today only because an empty vector converts to any declared element type on
construction) — should become `Vector{AbsSymmetry}(undef,0)` for consistency
with `TriangleBilliard`'s pattern, and because it will need to become a real
non-empty typed vector anyway once Step 11 needs `PolarBilliard` (or its
successor) to support symmetric polar deformations.

#### Gap 6 — No cross-check between `ReflectionSymmetry` boundary-condition markers, `billiard.symmetries`, and `solver.symmetry`

Three separate places currently encode "this billiard/solve has a discrete
symmetry", related only by user convention, with no validation linking them:
1. `ReflectionSymmetry{S<:AbsReflection}` — a **per-curve boundary condition**
   marking a fundamental-domain seam as a symmetry cut (e.g. Stadium's quarter
   sector walls).
2. `billiard.symmetries::Vector{AbsSymmetry}` — the **billiard-level** list
   used by `full_boundary`/`SymmetryOrbitMap` reconstruction.
3. `solver.symmetry` — the **solver-level** single symmetry a `SweepBIMSolver`
   is told to fold on (from Gaps 1–2, currently must be one of the exact
   types with a `symmetry_index_orbits` method).

Nothing currently checks that a `ReflectionSymmetry(sym, N_sectors)` marker's
`sym` is actually a member of `billiard.symmetries`, or that `solver.symmetry`
is compatible with `billiard.symmetries` (e.g. requesting `XYAxisReflection`
folding on a billiard whose `symmetries` only contains `XAxisReflection`).
This is a real class of silent-wrong-answer risk, but it is **new
functionality** (a validation helper), not a port from `-develop` (`-develop`
does not have this cross-check either) — see the improvement plan below for
how to scope this without over-engineering it.

#### Non-gap: no new boundary-condition type needed for rotational symmetry seams

Checked directly: `-develop`'s `StarBilliard`/`C3Billiard` (the two Cn-rotation
billiards that need a wedge-shaped fundamental sector) use the **already
existing** `QuantumSolverIgnore()` boundary condition on their two radial wall
segments — there is no `RotationSymmetry`-style boundary condition mirroring
`ReflectionSymmetry`, and none is needed. This resolves the question the user
raised about BC interaction for rotations: no new BC type work item follows.

#### Non-gap: billiard constructors — defer to Step 11, don't design upfront

`StadiumBilliard`/`TriangleBilliard`/`limacon.jl` (and `-develop`'s
`StarBilliard`/`C3Billiard` above) all follow the same three-part shape:
build `fundamental_domain` (with explicit per-curve `bcs` including
`ReflectionSymmetry`/`Transparent`/`QuantumSolverIgnore` markers), set
`symmetries::Vector{AbsSymmetry}`, wrap both in the `<:AbsBilliard` struct.
There is no shared constructor abstraction today, and introducing one now
would be speculative — Step 11 has ~10 new billiards to port, several of
which (`star.jl`, `c3.jl`, and potentially a symmetric `circle.jl` variant)
are visibly the *same* "polar billiard with `Cn`/`D_n` symmetry and a wedge
fundamental sector" shape. **Recommendation**: do not build a generic
constructor helper in this step; instead, Step 11's implementation plan
should look at its first two or three polar billiards side-by-side once
written and factor out a shared helper only if the duplication is real and
identical (per the mode's "avoid over-engineering"/"don't design for
hypothetical future requirements" rule) — flagged here as a note for whoever
writes Step 11, not as an action item of this step.

## Symmetry-framework extensibility assessment (user's specific question)

The user asked whether the symmetry framework could be made easier to extend
(add a new symmetry type, get correct dispatch everywhere "for free"). Finding:
**the framework is already reasonably extensible along the axis that matters**
— adding a new `<:AbsReflection`/`<:AbsRotation` subtype requires exactly three
things, all multiple-dispatch methods, no central registry or `if`/`elseif`
block to edit:
1. `apply_symmetry(sym, pt)` (`symmetry.jl`).
2. `symmetry_irrep_character(::Type{T}, sym)` (`symmetry.jl`).
3. `symmetry_node_multiple(sym)` + a `symmetry_index_orbits(::Type{T}, xy, sym)`
   method (`symmetryorbits.jl`) — plus, after item B above, an
   `_apply_symmetry_to_curve`/orientation-reversal classification
   (`_orientation_reversing(sym)`) entry in `fullboundary.jl`.

This is already the idiomatic "add a method, not a conditional" pattern this
codebase follows elsewhere. The one genuine inconsistency found (Gap 1) is not
a framework/extensibility defect — it is simply four methods that were
written before `symmetry_irrep_character` existed and never got updated to
call it. **No redesign is warranted**; items A–D above are the correct,
minimal-diff fix. Do not introduce an abstract "symmetry registry",
trait-dispatch table, or macro to auto-generate these three methods — three
explicit methods per new symmetry type is already idiomatic multiple dispatch
and matches every other extensibility point in this codebase (new
`AbsBasis`/`AbsSolver`/`AbsCurve` subtypes all work the same way).
