# Step 12.5 — `compute_spectrum` API consolidation & unfolding/geometry split

Status: **Implemented** (2026-09-12). Written up as a step file because it
is a scoped, ordered piece of work discovered while auditing
`spectra/spectralutils.jl`/`spectra/unfolding.jl` for API consistency,
independent of steps 12/13's multiply-connected-domain work but touching
some of the same `compute_spectrum`/`SpectralData` machinery Step 9.5 added.
Slotted at 12.5 (after Step 12's pure domain-abstraction refactor, before
Step 13's `CompositeBIMSolver` numerical verification) since it is likewise
a structural/API cleanup with no new solver numerics, and should land before
Step 13 adds another `compute_spectrum` consumer (the annulus verification
script) that would otherwise need to be written twice.

## Goal

`compute_spectrum` currently has **inconsistent, partly broken** dispatch
across the `AbsBasisSolver`/`AbsBIMSolver` hierarchy:

* `compute_spectrum(solver::AbsBasisSolver, basis, billiard, k1, k2, dk)` and
  `compute_spectrum(solver::AbsBasisSolver, basis, billiard, N1, N2, dN)`
  (`spectra/spectralutils.jl`, marked `#Needs total rework` at the top of the
  file) dispatch on the **whole** `AbsBasisSolver` hierarchy but internally
  call `solve_spectrum`, which is only implemented for `AcceleratedBasisSolver`
  (`solvers/acceleratedmethods/acceleratedmethods.jl`) — `SweepBasisSolver`
  has no working `solve_spectrum`, so this dispatch is a live foot-gun, not
  just style debt. The `N1,N2,dN` variant also reads `billiard.area`/
  `billiard.length`/`billiard.angles` as **struct fields**, which do not
  exist on the current `AbsBilliard` (`area`/`length` are functions;
  `angles` was only ever a Veech-triangle-specific field on the CAFB
  fixture built by `make_triangle_and_basis`) — this variant is dead code
  that would `MethodError` on any real billiard.
* `compute_spectrum(solver::BeynSolver, billiard, k1, k2; Rmax, ...)` and
  `compute_spectrum(solver::ExpandedBIMSolver, billiard, k1, k2; dk::Function,
  ...)` (Step 9.5) are correct, but have no `N1,N2` counterpart and take no
  `basis` (correctly — no `AbsBIMSolver` ever touches a basis).
* `spectra/unfolding.jl` mixes three unrelated concerns in one file: Weyl-law
  state-counting physics (`weyl_law`, `k_at_state`, `corner_correction`),
  pure Green's-theorem geometry (`area` on `AbsCurve`/`CompositeCurve`/
  `AbstractVector{<:AbsCurve}`/`AbsBilliard`), and symmetry-reduction
  bookkeeping (`symmetry_reduction_factor`, `maximal_symmetry`,
  `fundamental_area`) — none of which need anything solver-related, and all
  of which belong in `BilliardGeometry.jl` alongside `AbsCurve`/
  `CompositeCurve`/`full_boundary`/the symmetry types they already operate
  on, not in `QuantumBilliards.jl`'s spectra folder.

Consolidate to four solver-scoped `compute_spectrum` methods (only for the
two *accelerated* branches — `SweepBasisSolver`/`SweepBIMSolver` keep
`k_sweep` as their sole range-scan entry point, they were never meant to have
a `compute_spectrum`), move geometry into `BilliardGeometry.jl`, and add a
small set of exported Weyl-law utility functions (`state_at_k`,
`spectral_density`, `k_range_for_states`) so every future
`compute_spectrum`/adaptive-`dk` caller shares one implementation instead of
re-deriving `A*k/(2*pi) - L/(4*pi)`-style arithmetic per solver (as
`-develop`'s own `VerginiSaracenoSolver.compute_spectrum(N1,N2)` currently
does, inline, in `QuantumBilliards-develop/src/solvers/acceleratedmethods/vergini_saraceno.jl`).

## Design decision: no `basis`, no uniform `dk` for `AcceleratedBIMSolver` (confirmed)

`AcceleratedBIMSolver` never touches an `AbsBasis` (checked: `evaluate_points`,
`construct_matrices`, `solve`, `solve_spectrum`, and the existing
`compute_spectrum(::BeynSolver/::ExpandedBIMSolver,...)` all take only
`billiard`) and its two concrete solvers use genuinely different windowing
strategies (`BeynSolver`: Weyl-balanced disjoint contour windows sized by `m`
levels each, no `dk` concept; `ExpandedBIMSolver`: adaptive trial-`k` grid via
`dk::Function`). Confirmed by the user: this plan **drops `basis` from every
`AcceleratedBIMSolver` `compute_spectrum` signature** and keeps `dk` as a
solver-specific keyword (already `dk::Function` on `ExpandedBIMSolver`; not
applicable to `BeynSolver` at all) rather than forcing a uniform positional
argument that would be meaningless for one of the two concrete types. This
means the `AcceleratedBIMSolver` branch never gets a single shared
`compute_spectrum` body — multiple dispatch on the concrete solver type
(`BeynSolver` vs. `ExpandedBIMSolver`) is the entire mechanism, exactly as
Step 9.5 already established for the `k1,k2` methods; this step only adds
each concrete type's own `N1,N2` overload on top, per Phase 4 below.

## Implementation steps

1. **Move geometry** (`area.jl` in `BilliardGeometry.jl`, per "Files touched"
   above). Run both packages' `test/runtests.jl` — no numerical change
   expected, this is a pure relocation.
2. **Add `corner_angles(billiard)`** next to `_component_corner_locations`,
   replacing the broken `hasproperty(billiard,:angles)` pattern used today in
   the dead `N1,N2,dN` method. Verify against the Veech-triangle fixture
   already in `test/solvertests.jl` (known corner angles) as a manual sanity
   check.
3. **Rewrite `unfolding.jl`**: keep `corner_correction`/`weyl_law`/
   `k_at_state` as-is; add
   `k_at_state(state, billiard::AbsBilliard; fundamental::Bool=true)`
   (dispatches to `get_boundary_curves(billiard)`'s area/length/corner_angles
   when `fundamental=true`, matching what an `AcceleratedBasisSolver`/
   `AcceleratedBIMSolver` actually diagonalizes over, or `full_boundary(billiard)`
   when `fundamental=false`); add `state_at_k(k, billiard; fundamental=true)`
   (the inverse direction — evaluates `weyl_law` at the same `(A,L,angles)`);
   add `spectral_density(k, billiard; fundamental=true)` (`dN/dk = (A*k -
   L/2)/(2π)`, the derivative of `weyl_law`, replacing the inline `density =
   A*k0/(2*pi) - L/(4*pi)` expression `-develop`'s `VerginiSaracenoSolver`
   duplicates today); add `k_range_for_states(billiard, N1, N2;
   fundamental=true) -> (k1,k2)` pairing two `k_at_state` calls — the single
   place every `N1,N2` `compute_spectrum` method delegates to.
4. **Add `_finalize_spectrum`** to `spectralutils.jl`:
   ```julia
   function _finalize_spectrum(ks::Vector{T}, ts::Vector{T}, control::Vector{Bool};
                                ten2::Union{Nothing,Vector{T}}=nothing) where {T<:Real}
       isempty(ks) && throw(ArgumentError("compute_spectrum found no candidates in the requested range"))
       p = sortperm(ks)
       return SpectralData(ks[p], ts[p], control[p]; ten2 = ten2===nothing ? nothing : ten2[p])
   end
   ```
   Document in its docstring that it is safe to call from a single thread
   **after** a solver's own parallel region has already written into
   disjoint preallocated slots (this is how `BeynSolver`/`ExpandedBIMSolver`
   already operate — `ks_win[i]`/`tens_win[i]` per window,
   `ks_corr[i]`/`tens_corr[i]` per trial point — so no concurrent access to
   `SpectralData` construction itself ever occurs; `_finalize_spectrum` does
   not add any new thread-safety mechanism, it only removes duplicated
   sort/construct/empty-check tails). Replace the existing tails of
   `compute_spectrum(::BeynSolver,...)` and
   `compute_spectrum(::ExpandedBIMSolver,...)` with calls to it; verify
   byte-identical output on the existing Step 9.5 fixtures.
5. **Rescope + add the four `compute_spectrum` methods** (design confirmed,
   see above):
   * `compute_spectrum(solver::AcceleratedBasisSolver, basis::AbsBasis,
     billiard::AbsBilliard, k1, k2, dk; tol=1e-4, multithreaded=true)` —
     today's generic sliding-window/`overlap_and_merge!` body, re-scoped from
     `AbsBasisSolver` (fixing the false-dispatch bug), `dk::Union{Real,Function}`
     (constant step, or adaptive via the new `spectral_density`). Ends with
     `_finalize_spectrum`.
   * `compute_spectrum(solver::AcceleratedBasisSolver, basis::AbsBasis,
     billiard::AbsBilliard, N1::Int, N2::Int; N_expect::Real=1, kwargs...)` —
     calls `k_range_for_states` then the `k1,k2,dk` method above, with a
     `spectral_density`-adaptive `dk`.
   * `compute_spectrum(solver::BeynSolver, billiard::AbsBilliard, N1::Int,
     N2::Int; kwargs...)` — calls `k_range_for_states` then `BeynSolver`'s
     existing `k1,k2` method. No `basis` argument, no `dk` (not meaningful
     for Beyn's Weyl-window contour planning).
   * `compute_spectrum(solver::ExpandedBIMSolver, billiard::AbsBilliard,
     N1::Int, N2::Int; kwargs...)` — calls `k_range_for_states` then
     `ExpandedBIMSolver`'s existing `k1,k2` method (which already accepts
     `dk::Function` as a keyword; forwarded through `kwargs...` unchanged).
     No `basis` argument.
   These last two intentionally remain two separate one-line methods rather
   than a single `AcceleratedBIMSolver`-scoped method, since `BeynSolver`/
   `ExpandedBIMSolver` already have no shared `k1,k2` body to delegate to —
   adding an abstract-level method here would need its own `kwargs`
   pass-through indirection for no simplification benefit.
   Delete the dead `compute_spectrum(::AbsBasisSolver,...,N1,N2,dN)` method.
6. **Update exports** in both packages' top-level module files per "Files
   touched" above.
7. **Update `QuantumBilliardsTests/reference/*.jl`** call sites only if the
   narrower dispatch actually breaks them (expected not to, per the note
   above — verify, don't assume).

## Performance & fidelity notes

* This step touches no hot numeric kernel — `area`'s `quadgk` integration,
  the Beyn contour loop, the EBIM trial-grid loop are all reused unchanged;
  only their surrounding dispatch/API surface and file placement move.
* `_finalize_spectrum` must not be called concurrently from multiple threads
  with *overlapping* mutable state — confirmed safe because every existing
  and planned caller already funnels disjoint per-worker outputs into
  preallocated arrays before this single finalize call, matching the
  project's "inner single-threaded, outer parallel, disjoint writes" rule.
* Moving `area`/`fundamental_area`/`symmetry_reduction_factor` into
  `BilliardGeometry.jl` requires no new dependency: that package already
  depends on `QuadGK` (confirmed in `BilliardGeometry.jl/Project.toml`) and
  already owns `AbsCurve`/`CompositeCurve`/`full_boundary`/every
  `AbsReflection`/`NFoldRotation` type these functions dispatch on.
